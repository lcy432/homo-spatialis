## 一、已确认的原则（项目所有者，2026-10-05）

1. 固定城市，三个年度周期（N 是协议字段，默认 3）。
2. 每年一份 LLM 计划；环境在内部按月记账，**不增加月度 LLM 调用**。
3. 行动负责选择；收入、支出与执行由环境计算。理由文字不进入结算。
4. 收入可以累积，并用于同年后续月份的购买。
5. 付不起最低住房或最低食品时，分身出局。
6. 出局分身保留记录，不能从城市平均的分母里悄悄删除。

   > ⚠ 本条“城市平均的分母”已被 DECISIONS/0028 更正（所有者 2026-10-11 口径）：城市平均分排除已确认的生活出局者；原计划人数、出局比例（以原计划人数作分母）及原因的报告保留全部分身；模拟问题造成的未完成计算另作不确定性分析。出局分身保留记录、不复活，这一点不变。见该记录。
7. 终态编号 `x = N + 1`（N = 3 时 x = 4）。
8. 税表核查延后到 V2 前。
9. 满足感、精力反馈、风险、折现与期末计分属于后续轮次。
10. 保留商品异质性与多国家接口，不做真实跨国比较。

## 二、计划能表达什么

一年一份 `YearAction`。只用结构化字段，**不**从理由、目标或描述里提取，也没有脚本语言。

| 角色（由目录认定） | 时间字段 | 例子 |
|---|---|---|
| 住房、食品（在城市最低生活声明的合格名单里） | `start_month`、`end_month` | 第 1–12 月住单间 |
| 工作（带职业与报酬） | `start_month`、`end_month` | 第 1–12 月做行政文员 |
| 按月 / 按周计费的服务 | `start_month`、`end_month` | 第 1–6 月共享办公 |
| 培训（参与月份） | `start_month`、`end_month` | 第 7–12 月上簿记课 |
| 年付服务 | 只给 `start_month`（覆盖固定 12 个月，可跨入下一年） | 第 7 月办健身年卡 |
| 持续物品、一次体验 | `month` | 第 2 月买电脑；第 6 月听音乐会 |

* **计划里的先后就是同月竞争资金时的顺序**（在同一步之内），结果里原样记 `plan_order`。
* 数量本轮只支持整数；住房、食品、工作、培训的数量必须是 1。
* `minimum_fallback`：明确声明"某月付不起（或给不了）我选的住房/食品时，改用本城最低方案"。
* 安排项（如采购频率）照常校验允许值，**只记录、不定价**。
* 时间字段与角色不符、引用不存在、住房或食品不是每月恰好一项、数量不合法——都是**结算前**
  就能发现的输入错误。

例：计划"第 6 月买电脑，届时钱不够就拒绝"可以表达；"钱不够就推迟到第 8 月"不能表达，
本轮不猜。

## 三、月度结算

每个月固定七步：

1. 读月初现金；
2. 按当月在岗的工作计算税前收入，按**年内累计**计算合成税；
3. 收入入账；
4. 检查"最低住房 + 最低食品"是否付得起——**只检查，不扣款**。付不起即出局；
5. 付实际住房与食品，再按计划顺序付其他周期性费用（按月/按周服务、年付服务的当期付款）；
6. 按计划顺序执行当月的一次性购买、体验与培训报名；
7. 更新持有物服务月、培训参与月与月末余额。

**不能用未来月份尚未挣到的工资**：每个月只能花截至当月已经入账的钱。没有声明的借款、
透支或自动变卖。第 5 步付住房时，只能动用"为最低食品预留之后"剩下的钱——这样选了贵房子，
也不会把吃饭的钱挤掉；先付住房、再付食品是规则，不是隐藏的最优消费算法。

### 3.1 计费与服务期

| 报价 | 怎么收 | 怎么覆盖 |
|---|---|---|
| 按月 | 每个覆盖月收一次月价 | 只覆盖计划的月份（半年服务就是 6 个月） |
| 按周 | 年额 = 52 × 周价，按每月 52/12 周摊 | 同上 |
| 按年（年付服务） | 起始月一次付清，**不拆成分期** | 12 个月，跨年部分作为持有物带到下一年 |
| 一次性（物品、体验、学费） | 成交月付一次 | 物品从生效月起按月服务；体验当月发生 |
| 年薪 | 年薪 ÷ 12（按日历月序号摊） | 在岗的月份 |

### 3.2 精度与舍入

* 金额在内部一律是**整数最小单位**（`MoneyBasis.minor_unit_digits`，美元 = 分）。报价或
  现金的精度细于最小单位，是数据/输入错误，不是"差不多"。
* 年额按月摊用累计舍入：第 m 月 = round(A·m/12) − round(A·(m−1)/12)，四舍五入
  （ROUND_HALF_UP）。12 个月之和**恰好**等于 A。例：年薪 40,000 摊成 3,333.33 / 3,333.34 /
  3,333.33 循环；每周 40 的保洁摊成 173.33 / 173.34 / 173.33 循环，全年恰好 2,080。
* 守恒是精确等式：每月与每年都有"期末 − 期初 = 实际现金流合计"，没有容差。结算内部对此
  做断言，测试按整数分逐月核对。

## 四、最低生活与失败的分类

### 4.1 最低生活由数据声明

每座城在 `CityLifeCatalog.minimum_living` 里声明最低住房与最低食品：引用目录里**已有**的
项目、数量（本轮只支持 1）、计价依据（就是该项目的报价，须按月或按周计费），以及满足什么
最低需求（`meets`）。`qualifying_opportunity_ids` 列出哪些方案算满足这项需求（含最低方案本身）。

* 不从城市名、标签或 LLM 推断，也不拿规格不同的商品比价比出"最便宜"。
* 与偏好分开：最低生存标准与"想住大一点""想吃好一点"是两件事。
* 缺失、引用错误、不完整、最低方案不可得或带资格限制——一律是**数据错误**，绝不当成分身出局。

### 4.2 出局

第 4 步若现金 < 最低住房 + 最低食品，分身在这个月出局。钱**恰好**够就通过。记录：年、月、
当时现金、两项最低费用、缺口、缺哪一项。缺哪一项按"先住房后食品"归因：现金先算给最低住房，
剩下的再算给最低食品。两项费用原样保存，别的归因方式可据此重算。

最低生活优先于当月的任何自选支出；已经发生的支出不回滚；检查本身不是一笔扣款。

### 4.3 五种结算结果

| 状态 | 什么时候 | 账目 |
|---|---|---|
| `completed` | 正常过完这一年 | 提交；下一状态是下一年年初，或第 N 年后的终态 |
| `exited` | 付不起最低住房与食品 | 提交出局月之前（含出局月已入账的收入）的全部账目 |
| `plan_infeasible` | 所选住房/食品给不了（缺货、未知、不满足资格或付不起），最低生活仍付得起，且**没有声明兜底** | **什么都不提交**，带诊断（月份、可用现金、所需金额）退回计划方 |
| `input_error` | 结算前能发现的计划或状态错误 | 无 |
| `data_error` | 最低生活或税的配置缺失、引用错误或不完整；税函数输出不合法 | 无 |

**自选项失败不升级为出局**：按月服务某月付不起，就拒绝那个月（下个月按计划再试）；一次性
购买付不起，就拒绝且不顺延；年付或报名在起始月失败，本年对应的覆盖或参与全部落空。都记原因，
不给免费的收入或物品。

**兜底只按声明执行**：声明了某项需求的兜底，那一项从付不起的那个月起改为最低方案，直到该项
计划期结束（中途有钱了也不搬回去），结果里原项记 `downgraded_to_minimum`，兜底另成一条
`fallback_minimum` 记录并指回原项，可见反馈里写明原因。没声明就返回 `plan_infeasible`。
环境**不替分身挑没声明的替代方案**。

## 五、出局与终态

**出局之后**：保存出局年月、原因、缺口与当时的状态（`status = exited`，`year_index` 是出局
所在年，**不**被改写成 N + 1）；此前的现金流、物品与经历全部保留；出局月之后没有收入、消费、
培训与行动；之后再调用结算一律返回 `input_error`，不复活；分身不删除。出局分身本轮**没有**
满足感分数：不补零，也不做幸存者平均（E1-6）。

**模拟长度**：`LifeProtocol.simulation_years` 是协议字段（默认 3），正常行动发生在第 1–N 年，
终态编号 `terminal_year_index = N + 1` 由 N 推导，不单独配置。终态保存最后的余额、物品、技能、
目标与有限经历，不接受行动，不产生收入或支出，也不能构造观察。

**所有年份限制都查**，不只 `PersonYearState`：活跃状态 ≤ N、终态 = N + 1、出局年 ≤ N；
计划年份 ≤ N；持有物购入年份不晚于状态允许的年份、起用年份 ≤ N + 1；培训报名年份同理；
培训所需年数 ≤ N（原来写死的"≤ 3"从字段校验移到加载器，字段上只留防呆上限，N = 3 时 5 年的
培训照样被拒）。测试覆盖 N = 1、3、5。

## 六、物品、体验、培训与时间

* **持续物品**：一次买断（本轮只支持一次性付款），从生效月起每服务一个月剩余寿命减一个月，
  用完即移出持有物。`same_year` = 成交月起服务；`next_year` = 下一年第 1 月起服务（只对持续物品
  有定义）。年中购买**不会**平白少一年寿命：第 2 月买的 4 年电脑，第一年服务 11 个月，剩 37 个月。
* **E1-1 的年度期限**按 ×12 换成月（`remaining_years` → `remaining_months`，无信息损失；E1-1
  没有年中购买）。结算写出的新状态一律用月。
* **年付服务**作为"剩余覆盖月数"的持有物跨年；在仍被覆盖的月份里再预付同一服务是输入错误。
* **体验**只在发生时记录，从不变成持有物。
* **培训**：学费在首次报名的月份付一次；跨年继续参与不再收费；只记录已付费用、参与月份与
  进度（完成也只记"完成"）。**不**自动提高技能、工资或满足感（E1-5）。
* **资格**本轮词表：`occupation:<体系>:<代码>`、`skill:<名>>=<数>`、`training_completed:<机会 ID>`。
  词表外的标签是数据错误。资格在执行时按当月月初的状态判定：培训第 6 月完成，第 7 月起就满足。
* **时间**做基本一致性与预算检查（小时，精确分数，不用容差）：周期行动按请求月数摊年度时间
  成本，体验整笔计，持续物品与年付服务按本年服务月摊（含已有持有物）；声明了兜底的住房/食品
  取所选项与最低方案中较费时的那个，保证执行时即使降级也不超预算。**精力只记录**
  （`energy_feasibility = not_implemented`）：没有检查精力可行性，没有反馈。账务可行不等于
  完整生活可行。（2026-10-07：本条仍是生活规则 `e1-2-monthly-v1` 的行为；新规则 `e1-4a-monthly-v1`
  按月检查时间与精力、超限是计划不可行，见 [0020](0020-life-monthly-time-energy.md)。）

## 七、税：延后核查之前的底线

* 结算只接受显式的 `LifeTaxBinding`（函数 + 声明的策略 ID、状态、计价口径、税区）。没有绑定、
  城市没有配置税策略，都是数据错误——**没有配置不等于零税**。
* 本轮唯一允许的状态是 `synthetic_test_double`；没有 "verified" 状态。`SyntheticBracketTax`
  按 `SyntheticTaxPolicy` 的税档边际累进，口径或税区不符时**报错**，不回显标签。
* `worlds.taxes` 的现有税表与新生活协议的计价口径**尚未核查**，且旧接口缺少相应验证（不检查
  传入金额的口径，结果直接沿用传入的标签），因此本轮暂不接入（绑定时直接拒绝）。不做隐式货币
  转换或改标签。保留 `TaxFunction` 注入接口。

  > 订正（2026-10-06，[ADR0018](0018-life-exploratory-monthly-scoring.md) 第一节）：本条原写"按空间
  > 平减口径校准、会套错税档"，那是未经证明的推断。已改为上面的表述；延期核查的安排不变。
* 月度税与年度税的关系：第 m 月预扣 = round(T(年内累计税前收入)) − 截至上月的累计预扣。一个
  日历年就是一个纳税年度，跨所有工作累计；出局后不对没挣到的收入计税，截至出局的预扣恰好等于
  "全年只有这些收入"时的税额。税函数的 `year` 参数传计价基年。
* 结果标 `bookkeeping_label = synthetic_bookkeeping_only`，备注写明"不是真实税后生活成本"。
* **V2 前税表核查**（PLAN §3.0.1、§5）：币种、基年、当地标价 vs 空间平减收入、税辖区、适用年份、月度
  预扣与年度汇总。真实提供者必须显式通过这些检查，**不继承**合成测试的通过状态。

## 八、公开的简化（本轮做了选择，不是科学结论）

| 简化 | 为什么这样选 | 以后可能怎么改 |
|---|---|---|
| 降级持续到该项计划期结束 | 一年里反复搬家不现实；规则简单可审计 | 食品这类可按月切换的需求可以单独放开 |
| 按月服务付不起只拒当月、下月再试；一次性付不起不顺延 | 前者按月声明，后者只声明了一个月 | 若要"推迟到某月"，需要新的结构化字段 |
| 每月恰好一项住房、一项食品，数量 1 | 单人家庭；数量语义跨规格不可比 | 有家庭规模定义后再支持多份额 |
| 只支持整数数量 | 半件物品、半份工作没有定义 | 兼职比例等需要单独建模 |
| 最低方案须按月或按周计费 | 每月检查需要确定的月费 | 年付租约需要另定"月度最低"的口径 |
| 时间成本 × 数量 | 统一按"每单位"计 | 两张票是否两倍时间，可按类别另定 |
| 出局月的工资已入账、持有物不计该月服务 | 七步顺序里收入先于检查、服务在月末 | 若改成"出局月不计收入"需同步改税 |
| 年内累计预扣（免税额先用完） | 截至任一月份的预扣都等于"只有这些收入"时的年税，出局时无需退补 | 真实制度（如按月分摊免税额）在 V2 前核查时再定 |
| 有限经历只保留最近 12 条 | 控制状态大小 | 摘要的内容与长度属于 E1-7 的可见信息设计 |

## 十、本轮实现与验收

**实现了**：月度结算纯函数（`settle_year` / `settle_plans`）；合成税测试替身与显式绑定；
结算前的数据与计划检查（`ledger.life_catalog`，加载器与结算共用）；可见反馈的白名单投影
（`visible_feedback`）、只为活跃状态构造观察、观察里加入最低生活声明与培训进度；可结算的
E1-2 合成样例（三城、两人、对齐开局、七份计划，手算结果写在文件末尾）；离线检查脚本逐月打印
