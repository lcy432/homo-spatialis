# 0041 生活扩展：完整食品方案、个人消费与享受、装备与爱好

日期：2026-10-22（所有者批准范围内的 E1 局部执行、评分、期末估值改动与相应 E3 输入适配）。取代 [0034](0034-e3a-product-input-contract.md) 里“物质三项”的词表；其余接入规则不变。

## 背景

分身原来的物质生活主要是住房、新鲜食品和省家务的设备，休闲按“体验次数”计。这样的人生太窄：吃饭不能是一份完整的家常加外食方案，舒适用品与按摩这类享受没有地方算，爱好装备买了以后也不能和以后的活动连起来。扩展要做到“过得像人”，同时守住老规则：偏好不是开支比例，贵不等于更好，买不起不等于不喜欢，成交与持有本身不加分，未知不当零。

## 决定

1. **物质四项**：居住空间、饮食生活、日常生活便利、个人消费与享受（`e3a-vocabulary-v2`）。M = Σ 物质权重 × 四项分数，S = (1 − γ)B + γH 不变。旧确认不补齐，重新审阅；公共结构升为 `e3a-product-schema-v3`。
2. **食品是一个月的完整方案**（`LifeOpportunity.food_plan`）：组成（自己做 / 外食 / 外送）、每周餐数与新鲜餐数、菜系、做饭与外食小时。月费已含外食；时间、费用与评分读同一份方案。饮食生活只看新鲜餐与确认菜系的餐（SC-22），价格、档次、外食次数不是输入。代替正餐的活动套餐拒绝编入。
3. **享受按功能计**（`LifeOpportunity.enjoyment`）：在用的舒适用品按“有没有”，享受型服务按实际份数；同功能不叠加（SC-23）。纯爱好装备没有享受功能。
4. **装备与活动**（`equipment` / `activity`）：装备提供能力，活动写参与小时、往返与准备小时、需要的能力与套餐本次提供的能力。结算顺序：必要支出 → 当月一次性购买 → 有效持有 → 需要持有能力的活动；同一支付优先级下与 JSON 位置无关。买失败、病中取消、下一年才生效、到期都没有能力；套餐能力只对这一次有效。寿命按服务月扣一次，使用不再扣。每项活动每个请求月一条 `ParticipationRecord`，时间账、评分与记忆都读它。不连续的月份写 `ActionItem.months`，不另造编号。
5. **休闲改为参与小时**，确认兴趣只在同样的参与小时上放大（κ = 0.5，只看主类别，不放大城市背景；SC-24）。锚点重设：4 小时音乐会仍是 4。
6. **兴趣与口味**由 E3 按有限词表解释成候选，用户选中才进入画像（PI-26）；未答、暂不确定、没有固定爱好、通用评价、确认分开保存；品牌只留存。
7. **期末参考生活**用期末持有的装备：模板按功能排活动与享受服务，剩余寿命内用持有的，之后按模板替换或停止；各城同一套模板；模板没覆盖的期末能力报范围缺口（L/V/J 不变，不按购买价加分）。
8. 评分版本 `e1-life-v1`，规格 `score.e1-life.explore`，提示模板 `e3a-product-prompt-v2`。这些新语义进入画像、资料、评分、评价各自的身份；改动后要重新预检与确认。

## 后果

- 所有新数值都是探索设定（参数目录 SC-21–SC-25、PI-26–PI-27、EV-19、AG-23），在看 mock 结果前写定；不能据此排序真实城市。
- 真实资料（intake-02）没有做饭时间、新鲜餐数和活动参与时间，相应机会仍不能编进 E1；本轮只在合成样例上可执行。
- 代理看得到机会的这些事实与自己的参与记录，看不到评分公式、锚点、系数与参考分。
- 样例目录从 12 项扩到 24 项，请求变大：代理视野省掉说明文字与空字段（键不出现就是没有）。收尾修复之后的长度与上限见下一节。
- 生活扩展候选另有编译检查（收尾后 `e3-life-item-compiler-v2`）：只用 E1 契约与检查判定，不补价格、寿命、时间或限制。
- 真实模型会不会这样选，没有验证；本轮只用受控计划与 mock 证明因果规则一致。

## 收尾修复（独立审核 R1–R9，2026-10-22）

所有者授权：可以酌情提高单次输入上限；其余范围与数学不变（六维 + 独立健康、物质四项、已确认的分项公式与系数、工资税现金
疾病时间精力与反馈、L/V/J 与 C/E/M、年度规划与修订、预算、归档与恢复都不改）。

1. **R1 请求长度**：反馈只省重复、不删事实——内容完全相同的月份的资源账合成一条，参与按活动汇总、相同月份合成一段，机会里的
   空字段（含期限与时间精力里的 null）不序列化。单次输入上限按已核对的模型长度定（`common.life_planning_contracts.MODEL_LIMITS`）：
   Flash 与 Sonnet 128,000，Haiku 72,000（本机没有 Haiku 上下文的核对记录，按 200,000 的保守下界减去所有者定的 128,000 输出）。
   运行配置加载时检查输入 + 输出不超过上下文、输入上限不超过报价分档的适用上限；超限请求仍在发送前拒绝。预算额度不变。
2. **R2 隔离**：饮食、享受、参与的评分规格与月度明细，模板的爱好活动规则登记为内部类型；匹配结果与加权小时登记为保留键；结算的
   参与记录本身不进观察。
3. **R3 默认零**：食品组成的新鲜餐数与菜系、活动的“是否替代正餐”必须写；`null` 是资料未知，让相关评分未知，不当 0。
4. **R4 覆盖**：覆盖报告读饮食、享受与参与的事实，判断与评分器共用同一份函数；未支持、资料未知、确定没有发生分开表达。
5. **R5 编译检查 v2**：候选放进城市目录的副本跑 E1 的目录、跨对象与可结算检查并核对执行角色；种类与事实对不上、候选自带的日期 /
   年龄 / 资格限制、确定不可得都不再报“可执行”。仍然只有受控样例，没有接真实导出。
6. **R6 暂停**：一次性享受服务生病暂停只记暂停，不写参与记录；补上不连续月份活动暂停的回归测试。
7. **R7 兴趣**：原文在任何作答状态下都保留；重复类别在审阅阶段拒绝；没有按具体兴趣或口味个性化时要知悉
   `ack:interests_not_personalized`，预检查与结果写明范围；品牌与没认出的描述不再交给分身（与能力清单一致）。
8. **R8 期末范围**：期末持有的装备，参考模板考虑了哪些用途、哪些没有，作为公开的 `valuation_scope` 进入每个分身的结果；不改 V，
   不归 M。样例加一把能用 5 年的网球拍（已有的装备类型）与一个演示用的 mock 受控行为 `buy_hobby_gear`。
9. **R9 参与同源**：资源账从参与记录取主动活动的次数与小时（每小时负担仍取资源事实）；时间账、休闲评分、反馈与记忆读同一份事实。
