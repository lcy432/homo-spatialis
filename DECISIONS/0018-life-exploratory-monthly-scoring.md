## 一、E1-2 收尾

### 1.1 最低方案与合格目录矛盾：数据错误，不是出局

审核复现：最低住房声明 900、最低食品 400，目录里另一套**已被认定合格、可得**的住房 500；
分身现金 1,000，选 500 的住房 + 400 的食品——这个月明明过得下去，旧代码加载通过，却按
1,300 的门槛判第 1 月出局。复现测试（`tests/life/test_settlement_closure.py`）在修复前确实得到
`exited`，修复后得到 `data_error`。

**规则**：最低方案的声明不能与目录中已知可得、满足同一最低需求的方案相矛盾。比较口径：

* 数量都是 1（最低方案数量只支持 1，住房/食品计划项数量也必须是 1）；
* 同一个日历月逐月比较；
* 同一套月度计费换算（按周计价按每月 52/12 周，累计舍入）——**不拿不同规格的原始标价直接比**。
  例：周价 207 折成每月 897 < 900，矛盾；周价 208 折成每月 901.33/901.34，不矛盾。

只要某个月有别的合格项更便宜，就是矛盾 → 数据错误（加载器的 `settlement_problems`，结算的
`data_error`）。同价不算矛盾。不可得、未知（没有报价）的项不参与比较。**更便宜的合格项若带资格
限制**，就是"只对部分人开放的优惠"，本轮单一的最低方案表达不了"因人而异的最低"，明确拒绝这种
配置。本轮**不**增加自动找最便宜住房或替分身购买的功能。

为了让加载器与结算用**同一份**金额算法，报价 → 年额 → 按月份额的换算从结算抽到
`common/life_billing.py`（纯函数，两边都引用，没有循环依赖）。正常样例与"恰好够最低生活费"的
边界测试照常通过。

### 1.2 税表表述订正

ADR0017、契约说明与绑定错误消息里"旧税表已按空间平减后的美元校准、因此必然套错"是**未经证明
的推断**，订正为：**旧税表与新生活协议的计价口径尚未核查，且旧接口缺少相应验证（不检查传入金额
的口径，结果直接沿用传入的标签），因此本轮暂不接入。** 不重新研究或改造税表，不改旧实验结论，
合成税边界不变；V2 前税表核查照旧延期（PLAN §3.0.1、§5）。

### 1.3 依赖安排保留；`plan_infeasible` 的含义

本轮接受 `econ` 复用 `ledger` 的现有检查函数，不因目录命名返工。**E1-4 待办**：时间与精力规则
扩展时，把"数据加载"和"决定行动是否可行的规则"进一步分清，共用一份实现。

`plan_infeasible` 是**整份年度计划试算失败、不提交账目**——不是"已经生活之后回滚时间"。将来 LLM
的试算诊断、重试次数及其信息条件属于 E1-7。

## 二、本轮采用的实现规则

### 2.1 评分在哪里、读什么

评分读**一年已经结算好的实际记录**，逐月输出：分身实际享受了什么、各分项与七维满足感、哪些硬
要求没满足、每个数从哪条记录来。输入只有：协议与评分规格、城市评分条件、城市目录（读项目规格）、
这一年**年初**的状态（解释已有持有物）、结算结果、明确来源的评分偏好、结构化硬要求。**签名里没有
计划与理由**：不按原计划、理由文字或"想买什么"评分。评分只读不写，不改余额、物品或行动；结算不
依赖评分。人、城市、年份、协议、规格与结果必须配套，拿另一座城的生活记录配当前城市的评分资料
会被拒绝。

### 2.2 探索函数

对生活条件分项 j：

$$
z = b + \sum \eta\,x,\qquad s=\min\!\Big(c,\ \frac{z}{z+\tau}\Big)
$$

| 符号 | 含义 | 谁定、能否因城而异 |
|---|---|---|
| x | 该月**实际**得到的数量或条件（来自结构化规格与执行记录） | 记录 |
| b | 城市基础条件，与 η·x 同一单位 | 可因城而异，须带来源 |
| η | 声明的改善效率或单位换算系数（≥ 0） | 可因城而异，须带来源 |
| τ | 共同锚点（> 0）；不受上限限制时 z = τ 对应 0.5 | **只在评分规格里，所有城市共用** |
| c | 这座城这项条件可达的满足感上限（0–1） | 可因城而异，须带来源 |

* 限制 z ≥ 0、η ≥ 0；**负向作用本轮不支持**（不利城市用较低的 b、η 或 c 表达）。
* 基础条件单独不得超过上限：b/(b+τ) ≤ c，加载器检查。
* τ 在结构上就不能按城市调：城市条件对象没有这个字段。同一评分规格内不为得到预期排名调锚点；
  不把本城最好条件归一成满分。

**为什么可解释**：τ 是"半满"的位置，c 是这座城的天花板，b 是不花钱也有的部分，η 是同样一份改善
在这座城值多少；s 有界、单调、收益递减，逐项都能手算。**限制**：没有项目之间的交互、没有享乐适应、
没有时间与精力（E1-4）、没有负向作用、参数没有经验标定。**与旧静态效用的区别**：旧模型
（`econ.utility`）是 Cobb-Douglas 对数效用，并假设消费者已经最优分配了消费——它回答"给定预算的
最优福利"；这里评价的是**实际执行**的安排，分数有界在 0–1，与 ln V 不可比，不能把旧间接效用直接
当成任意生活行动的评分器。

### 2.3 评分来源表（防重复计分）

| 实际记录 | 读哪个字段 | 进入的分项（E1-3 样例） |
|---|---|---|
| 实际住的居所（含降级后的最低方案） | `ItemExecution.covered_months`，role=housing | 居住面积（规格 `floor_area_sqft`）、工作空间（规格 `home_office`） |
| 实际吃的食品方案（含降级后的） | `ItemExecution.covered_months`，role=food | 新鲜食品（规格 `fresh_meals_per_week`） |
| 执行了的按月/按周服务 | `ItemExecution.covered_months`，role=periodic_service | 工作空间（规格 `workspace`）；锻炼（声明了 `visits_per_month` 的才算） |
| 发生了的一次体验 | `ItemExecution.covered_months`，role=experience | 休闲（次数） |
| 年付服务的覆盖月 | **只读** `HoldingService`（不读 ItemExecution 的镜像） | 锻炼；工作空间 |
| 持续物品的服务月（含年初已有的） | **只读** `HoldingService`（成交本身不计分） | 耐用品（件数） |
| 工作、培训、现金 | 不是评分来源 | — |

据此防住：同一次服务在 ItemExecution 与 HoldingService 里计两次；买耐用品时奖励一次、再把同一笔钱
当持续收益反复奖励；房价高就住房分高（面积从规格读，价格从不进入计算）；同一空间需求被住宅和
共享办公重复满足（`any` 只计一次）；当前现金与未来消费提前计分（现金与工资不是来源）。省时与休闲
的重复计入不会发生，因为本轮**没有**以小时为单位的休闲来源（时间留给 E1-4）。本轮**不复用**旧城市
属性（`worlds.attributes`、`CityRecord.amenities_scaled`）：它们的方向、单位与标度版本还没有与这里
的锚点核对过映射，基础条件全部是显式写出的合成值。

### 2.4 合并方式

只实现三种，没有通用表达式语言：`sum`（同一单位可相加）、`max`（只取最好的一项）、`any`（布尔
替代，同一需求多处满足只计一次，用一个 η）。结果里每一项改善都标 `counted`，总有
z = b + Σ（计入的 η·x）。

### 2.5 购买与使用

区分三类：持有即持续提供的条件（居所、耐用品）、需要实际参与才产生收益的服务、一次体验。本轮
不增加使用决策；新样例把"年卡＋每月 8 次锻炼"声明成**行为方案**（规格 `visits_per_month`，时间按
次数计入）。**这是本轮的使用假设**：没有使用安排的年卡**不会**被自动解释成完整的健身收益（它在
评分里不是锻炼来源，报告会列出"在用但没有带来计入的改善"），E1-2 样例的年卡含义不变。

### 2.6 七维聚合

复用 `worlds.dimensions` 的七维名称与顺序。物质维 s_material = Σ m_j s_j（m_j 是这个人的物质细项
权重，非负、和为 1）；月度分 u = Σ w_k s_k（w_k 是七维权重，非负、和为 1）。权重不随城市变化，不用
实际花钱比例冒充偏好。E1-3 样例的输入逐项是：

| 维度 | 输入 | 可改善部分 |
|---|---|---|
| 物质 | 居住面积、新鲜食品、私人工作空间、耐用品四个细项 | 全部来自实际执行记录 |
| 休闲 | 城市基础 + 声明了使用安排的锻炼次数 + 实际体验次数 | 锻炼、体验 |
| 安全、医疗、机会、环境、通勤 | 只有城市基础条件 | **当前没有行动改善机制** |

工资、付款与现金余额本身不发放满足感；培训本轮不计收益（是否把"参加培训的当月体验"计入机会维
留到 E1-5），也不提前计算期末资产。

### 2.7 完整年份

只有十二个月都是 `scored` 才输出 annual_mean = Σ u_m / 12。**先逐月评分再平均**，不先平均物理条件
再套非线性函数（半年共享办公：逐月平均是 0.65，先平均条件再套函数会得到 0.714，后者是错的顺序）。
不做三年折现、不加终值、不跨分身平均、不输出城市推荐排序。

### 2.8 偏好来源

* 研究路径：合成设定的已知偏好（`InternalPreferenceTruth`）。
* 产品路径：只用用户明确提供的数值，按声明的规则换算——七维定和点数 / 100，物质细项定和点数
  （新增的可选字段 `StatedLifeProfile.material_points`）/ 100。**不**把 low/medium/high 当成 1/2/3，
  **不**从自由文字臆造数值；物质维有正点数却没有物质细项数值时返回"偏好信息不足"，不补均匀权重，
  也不借用研究真值（产品换算函数的签名里拿不到真值）。产品解释写"按你提供的偏好和当前模型计算"，
  不声称知道真实幸福权重。
* 现有序数偏好怎样形成数值权重，是后续的产品输入设计问题，本轮不新增问卷、不调用 LLM。

### 2.9 硬要求

硬要求要有结构化的可检验条件、替代关系与时间范围。条件词表：`category`（必须给）、
`min_<键>` / `max_<键>`（规格数值 ≥ / ≤）、其他 `<键>`（规格相等）；范围本轮只有"每个月都要满足"。
逐月输出满足 / 不满足 / 因数据不足无法判断（规格缺要比较的键）/ 未生活，并给出满足它的实际项目。
六个月满足就是六个月满足，只有十二个月都满足才是 `satisfied_every_month`；出局那年最多
`satisfied_in_lived_months`。硬要求单独报告，**不**进分数、**不**触发出局、**不**额外扣分，也不用
其他维度的高分抵消。描述文字从不解析。

### 2.10 缺失、降级与出局

* 已知没买/没执行某项改善：该项新增作用为零，城市基础条件照样存在。
* 数据未知：保留未知；有正权重的分项未知 → 该月总分不完整（`incomplete`，给分项与原因，不生成伪
  完整总分）；不逐城删除缺失需求再重新归一化；零权重项的缺失不阻断。共同子集比较、允许损失多少
  权重等规则留到后续，**不**把早期讨论的 50% 门槛设为默认值。
* 降级后的月份按实际得到的住房和食品评分，不加"失望""预期落差""搬家痛苦"等扣分。
* 月度状态：`scored` / `incomplete` / `exit_month`（工资已入账，但这个月没有过完）/ `after_exit`
  （没有继续模拟）。后两种不评分、不填零，也不当普通缺失跳过后算年均；出局月份与剩余期间怎么
  计入完整轨迹留 E1-6。

### 2.11 信息隔离

评分规格、城市评分条件、评分偏好与各层评分结果都是内部对象，加入可见观察的第二道扫描（每一种
都单独测过）；代理观察与事实反馈不含分数。用户自己的陈述照旧按许可可见——新增的物质细项点数
由显式许可 `show_stated_material_points` 控制，研究文字条件下隐藏。

### 2.12 三种"能不能"分开

记账能否执行（生活输入的 `settlement_ready`）、探索月度评分能否执行（评分配置的
`exploration_scoring_ready`）、完整生活协议能否用于正式评价（协议的 `scoring_ready`，本轮 false）。
没有靠把待定政策标成 decided 来解锁演示。

## 五、手算例子与验收证据

u01 在 A31 第 1 年第 2 月（研究真值；合成）：住房单间 500 平方英尺 → z = 0.01 × 500 = 5，s = 5/10 = 0.5；
基本食品每周 3 顿新鲜餐 → 3/10 = 0.3；共享办公 → z = 1 + 3 = 4，s = 4/5 = 0.8；第 2 月买的电脑当月
起用 → 1/2 = 0.5；物质 = 0.4×0.5 + 0.1×0.3 + 0.3×0.8 + 0.2×0.5 = 0.57。五个基础维各 0.5，休闲只有基础
4/16 = 0.25。月度分 u = 0.35×0.57 + (0.15 + 0.10 + 0.15 + 0.05 + 0.15)×0.5 + 0.05×0.25 = 0.512。全年
(0.477 + 4×0.512 + 0.5195 + 6×0.493)/12 ≈ 0.50021。

验收（`tests/life/`）：本轮新增 52 条（收尾 5、评分 37、配置 10），覆盖验收 1–14 与手算核对；十一处
关键保证做过变异测试（逐条破坏后均有测试失败，恢复后全部通过）；离线演示把输入指纹、未提交状态、
结果与九条手算核对写在 `runs/2026-10-06-e1-3-scoring-demo/`。
