> **当前规则一览**
>
> * **规划器只拿安全投影**：请求 = 许可投影的观察 + 城市背景事实 + 获准的记忆 + 公开规则 [+ 上一份候选的安全诊断] + 元数据，逐字段构造并扫描，
>   交给规划器的是纯 JSON；规划器拿不到内部运行 bundle、研究真值、评分配置或完整内部状态。
> * **输出只认一个 JSON 对象**：需求摘要、计划理由、年度行动；身份由运行器填写；多写字段是格式错误；不执行输出里的代码。理由进
>   `YearAction.rationale`、需求摘要只进规划记录与下一年的代理自述——只改它们，生活结果完全相同。
> * **城市背景事实**：可见事实表（含义、数值或类别、单位、已知 / 确定不存在 / 资料未知、时间口径、来源性质）与内部换算（b = 0.5 × 指数，来源分开）；
>   开跑前逐项核对，已知事实换算的 b 与评分条件逐位相等，未知只对应未知，有背景的分项都有可见事实；运行中核对目录与事实的身份。
> * **执行前检查** `check_year_plan`（与结算共用 `_screen` 与无事件月度执行器，什么都不提交）；**能不能修订按阶段与问题代码判断**；每年 1 + 2 份候选；
>   诊断服从信息许可；修订耗尽就停在规划阶段，不替分身挑方案、不换规划器、不补分、不换人。
> * **真实执行之后的事件不重来**：疾病、出局、停止、反馈受阻都按已有引擎保留，不回到年初重问、不重抽。
> * **失败范围**：生活出局、停止、修订耗尽只停这个分身；城市资料问题只停这个分身并标明城市；共享配置或未知程序错误暂停批次；没轮到的保留为未运行；
>   原名单不缩小。
> * **E1-6 口径不变**：只调用 `evaluate_clone` 与 `aggregate_arm`；部分轨迹带 `PlanningStop`，汇总按原因细分（修订耗尽 → 计划或执行未完成、城市资料 →
>   资料缺失、调用上限 → 未运行）；分类与公式不变。
> * **归档、重放与恢复**：运行清单记下全部内容身份；重放用接受的行动经真实执行入口重建（0 次规划调用）；恢复先核对身份，复用已记录的回答，尝试次数与
>   调用次数不清零；身份不符就拒绝。

## 一、所有者的要求（本轮 prompt）

1. 本轮用可控的 mock，不调用真实 LLM；A 的成功不能当作模型行为能力的证据。真实模型接线与付费试跑归 E1-7B，真实资料归 E3，前端归 E5。
2. 分身固定城市、默认三个行动年；一年一份计划，环境按月执行；同一用户的原始偏好固定，消费与工作选择可以随城市、余额与经历变化。
3. 城市事实、代理输入与未来真实资料必须对齐；不能把 `CityScoringConditions` 开放给代理，也不能把隐藏的 b、c、η 换个字段名发出去。
4. 每年 1 次正常规划、最多 2 次修订；网络重试与计划修订分开；不伪造 token 与费用。
5. 健康协议的无事件试算与真实事件路径不能只凭一个状态字符串区分；用明确的执行阶段与诊断来源。
6. 失败按范围处理；原名单不缩小；不用宽泛的异常捕获把错误当成普通缺分。
7. 复用 E1-6 的评价与聚合；第 2 年规划失败不能抹掉第 1 年。
8. 保存可核对的记录；重放不重问模型、不手工设置封存标记；支持年度边界恢复，身份不符就拒绝。

## 二、采用的规则

### 2.1 执行前检查的公共入口（econ，最小提取）

`econ.life_settlement.settle_year` 的前四步（参数类型 → 状态能否接受行动 → 城市资料 → 年初状态 → 计划）原样提取成 `_screen`，返回（阶段，失败结果）。
新增 `check_year_plan`：`_screen` + 一遍 `_Year(..., new_events=False)` 的逐月试算，返回 `PlanCheck`（阶段 `arguments` / `state_status` / `city_data` /
`state` / `plan` / `no_event_trial` / `passed`、状态与问题），**不返回账目或下一年状态**。`settle_year` 改为调用 `_screen`，检查顺序、问题代码、说明与
执行结果逐字节不变（生活模块原有 916 条测试与旧演示的兼容比较证明）。无事件试算里不会出现 `stopped`：失败直接返回计划不可行或资料错误；停止只发生在
真实事件之后——检查对此加了断言。

### 2.2 处置（`orchestration.life_runner.classify_check`）

| 阶段 | 处置 |
|---|---|
| 解析失败（格式） | 修订 |

### 2.3 城市背景事实

`common.life_city_facts`：`CityFact`（`known` 必须有值；`unavailable` 与 `unknown` 不带值，`unknown` 必须写原因）、`CityFactSheet`、内部 `FactScoringLink`
（`linear_base_v1`，系数为正、精确十进制；`unavailable_base` 不写就不允许"确定不存在"；来源不能是 `observed`）。检查在 `ledger.life_city_facts`（见技术说明
3.2）。可见投影 `VisibleCityFact` 不含换算；`FactScoringLink`、`CityFactsConfig` 登记在禁止进入 payload 的类型里，换算键登记为保留键。

### 2.4 请求、输出、诊断与记忆

见技术说明第 4–6 节。长度上限：响应 20,000 字、上一份输出原文 4,000 字、需求摘要 400、理由 1,000；记忆最近 3 年事实、每年 8 条、每条 240 字，代理
自述只上一年（200 / 400 字）。诊断：精力可见时给额度、用量与超出量；隐藏时只说超了额度并列出各项负担（公开成本），不给数字。

### 2.5 规划停止的契约扩展（评价交接）

* `common.life_evaluation_contracts.PlanningStop`（年份、种类 `revisions_exhausted` / `city_data` / `budget_exhausted`、调用次数、问题代码、说明），
  `TrajectoryRecord.planning_stop`（只能接在 `not_finished` 的最后一年之后；没有用到时不序列化）；
* `econ.life_evaluation.evaluate_clone(planning_stop=None)`：核对后写进轨迹记录并加一条原因；L、V、J 的算法不变；
* `common.life_aggregation_contracts.RunFailure`：`stage` 增加 `planning`，可带 `planning_stop`（只能是第 1 年、可预期的失败）；`PLANNING_STOP_REASON`；
* `econ.life_aggregation`：`_missing_reason` 对带规划停止的 `not_finished` 按映射给原因；`classify_arm` 对带规划停止的 `RunFailure` 同样处理（没有轨迹，
  K = 0）。C / E / M 的分类与范围公式不变；已有结果逐字节不变。

### 2.6 调度、预算与失败

顺序调度（名单顺序）；全局调用上限（样例 60）；预算用尽时正在规划的那一年停下（`budget_exhausted`），一次调用都没轮到的分身记为未运行；共享配置、契约
冲突或意外异常记为这个分身的程序错误（`RunFailure`，不提取已知月份）并暂停批次；城市资料问题只停这个分身。运行前输出支持范围说明。

### 2.7 归档、重放与恢复

见技术说明第 9 节。运行清单的身份集合：规划接口版本、运行配置、冻结名单、协议、评分配置与评分内容、城市事实（可见与对应）、许可、提示模板、记忆政策、
规划器与受控行为、事件来源、各城目录与税、各运行臂的评价内容、关键代码文件。

## 四、本地实现选择（prompt 没有写死，请所有者复核）

1. **执行前检查对没有随机事件的协议跑完整的确定性一年**，真实执行时再跑一遍（纯函数，结果相同）。代价是两倍计算，好处是检查与执行共用同一份代码。
2. **能修订的范围**：`plan` 阶段的全部问题（除运行器填写的身份与年份）、无事件试算的资源超限与住房食品给不了、以及唯一一种资料错误
   `treatment_data_unknown`；其他资料错误一律当城市资料问题，不让分身去"绕开"可能损坏的资料。
3. **程序错误不保留已知月份**：出了意外错误的分身作为 `RunFailure`（意外）进汇总，之前提交的年份留在归档但不进评价——不假定之前的轨迹仍然可信。
4. **恢复也支持"两份候选之间"**：已记录的回答复用（核对请求指纹），从下一份候选继续；这比只在年度边界恢复多一步，但不重复调用、计数不清零。
5. **mock 的规则**（第 10 节）与受控行为写进运行配置并进入运行身份；β 的"物质与发展点数为 0 就不为多挣钱换岗"是 mock 读偏好的唯一方式之一，不是对
   真实模型的期望。
6. **城市背景事实用 0–10 合成指数与 b = 0.5 × 指数**：保持与 E1-6B 评分条件逐位相等，样例的业务数字因此可以直接沿用 E1-6B 的手算。
7. **记忆的固定顺序与上限**（技术说明第 5 节）是工程约定，不是记忆心理学结论。
8. **CLAUDE 硬规则 7 的适用范围**：生活协议的年度事实记忆与每年 ≤ 3 次单轮规划调用不是"记忆流"或"多轮对话"；旧静态研究实验的条件不变。

### 6.1 F1：恢复时核对归档记录（恢复必须继续原来那次模拟）

审核反例：第 4 次调用（A95 r1 第 1 年第 1 份候选，原检查记录是"精力超限、要修订"）的原始响应被换成合法的第二份草稿，指纹与检查记录都不动，
原来的恢复入口 0 次新调用就接受并执行了它。规则：

1. **一份共用的归档核对**（`orchestration.life_runner.load_archive_records`），恢复与重放都在继续执行、调用规划器或追加任何记录之前调用：
   * 键不重复——调用与检查记录按（分身、年份、第几份候选），已接受的行动按（分身、年份）；重复就拒绝，不用后一条覆盖前一条；
   * 调用记录：请求编号与身份；存下的请求重算的指纹（`payload_fingerprint`）等于 `request_fingerprint`；重新渲染的提示文字指纹相同；规划器身份与
     运行清单相同；原始响应与规划器错误恰好有一个；
   * 检查记录：有对应的调用；请求编号与请求指纹相同；原始响应重算的指纹等于 `response_fingerprint`；
   * 已接受的行动：指向处置为 accepted 的那一份候选；行动、行动指纹与检查记录一致；用已有的 `parse_output` 解析那份原始响应得到的就是它；
   * 支持的中断位置：只有最后一次调用可以没有检查记录（响应已落盘、检查尚未落盘），也只有它的 accepted 检查可以没有已接受的行动（检查已落盘、
     年度尚未执行）；其他缺口拒绝。重放已经结束的运行时一处缺口也不允许（记为程序错误的分身除外）。
2. **按同一套代码重放比较**：恢复从第一个分身起重走已经记录的路径——复用原始响应，用原有的解析、执行前检查（`check_year_plan`）、处置
   （`classify_check`）与执行（`run_life_year`）重新得出检查记录、已接受的行动与分身结局，逐项与归档比较（`_attempt`、`_commit`、`_record`）。归档层
   不另写计划判断。年度已执行并归档的，照重放逻辑重建，不重复征询规划器、不重复累计生活结果。
3. **先核对、后写入**：重放阶段不写任何文件、不调用规划器；第一次需要写新记录或调用规划器之前，所有已有记录（调用、检查记录、已接受的行动、
   进度里已经结束的分身结局）都必须已经重放到，否则拒绝（`_leave_replay`）。重放阶段遇到意外错误也拒绝恢复，不记成分身的程序错误。
4. **冲突是运行归档的问题**：`RunRefusedError` 写明分身、年份、第几份候选与不一致的字段；不归为生活出局，不靠重新询问规划器掩盖；拒绝后原归档
   一个字节都不变、规划器 0 次调用。这是工程一致性检查，不是防恶意伪造（同时改写全部记录与指纹的归档不在范围内）。
5. 不承诺数据库事务或任意断电修复：本程序声明支持的中断位置只有上面两种加年度边界与两份候选之间。

### 6.2 F2：实际规划器的设定必须与声明一致

审核反例：运行配置声明了两段受控行为，调用方用了没有传受控行为的 `RuleBasedMockPlanner()`，运行器只比名字与版本就放行（27 次调用变 25 次，
原本第 2 年规划失败的 B96 r3 完成三年）。规则：

1. 规划器接口新增 `effective_spec()`：报出实际生效的设定（`PlannerSpec`：身份与影响行为的设置）；mock 报出它真正持有的受控行为。
2. 行为身份 `PlannerSpec.behavior_fingerprint` 包含：身份的种类、编号、版本、规则版本、模型快照（**不含**说明 `note`）；每段受控行为的分身、行为与
   年份（**不含**说明）。mock 按"这个分身这一年有哪些行为"的集合取用受控行为，所以受控行为之间的先后、年份的先后与重复都不影响行为，内容身份里
   按分身与行为排序、年份去重排序。E1-7B 的真实模型设置（温度、token 上限、服务重试）将来加进 `PlannerSpec` 并进入行为内容，本轮不实现。
3. 新运行在建归档与第一次规划调用之前、恢复在读任何归档记录之前核对（`planner_setting_problems`）：身份逐字段相同，行为身份相同；不同就拒绝，
   写明声明了但实际没有、实际多出、年份不同的受控行为；不报设定的对象不能作为正式运行的规划器。运行清单新增身份 `planner_behavior`。
4. 测试替身照样可以接入：继承 mock 或自己实现 `effective_spec()` 即可，运行器不写死某一个 Python 类。

### 6.3 F3：事实记忆按真实领薪月份写区间

审核反例：A95 r1 第 2 年第 5 月病假没有工资，领薪月份 1–4、6–12，记忆却按最小、最大月份写成"领到工资的月份 1–12 月"。规则：

1. `agentlayer.life_planning.month_ranges` 从真实月份生成区间、保留中间缺口，并写月数："第 2 年：岗位 a95.job.accountant_office 领到工资的月份
   1–4、6–12 月，共 11 个月"；单月写"5 月"；一年没有领薪写"这一年没有领到工资"。
2. 多份岗位各写各的月份，不拼成一段连续经历。不新增 LLM 总结器、心理状态或记忆容量；事实与代理自述照旧分开。
3. 核查过同类写法：记忆里只有岗位月份用了"最小–最大"；学习一行写的是参加月数（"参加 N 个月"），不是区间，没有同样的误述，未改。
