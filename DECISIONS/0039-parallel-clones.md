# 0039 每个分身并行地过生活

日期：2026-10-19（所有者决定）。取代 [0030](0030-life-e1-7a-agent-planning-loop.md) 里"顺序调度（名单顺序）"的那一条；其余规划、修订、记忆、归档与重放规则不变。

## 决定

- `LifeRunner` / `start_run` / `resume_run` 有 `workers` 参数：同时在过生活的分身数。1 是顺序（库函数的默认值，测试与离线桥接沿用）；大于 1 时每个分身一个线程任务。
- 入口脚本默认所有分身并行（最多 `DEFAULT_MAX_WORKERS` = 16 个，`--workers` 可改）：`scripts/run_life_e1_7b.py` 的 main / resume / mock 与 `scripts/run_product_full.py`。先导（pilot，名单第一项的第 1 年）固定顺序。
- 并行不改变结果：分身的生活只取决于自己的计划与运气（疾病随机键不含遍历顺序），所以每个分身的结局、绑定、评价与城市汇总与顺序运行逐项相同；只有归档里记录的先后不同。

## 共享状态怎么处理

| 共享的东西 | 做法 |
|---|---|
| 全局调用上限、"停在第 N 次调用之后" | 发送前在锁里占一个名额（已用 + 进行中），并行时也不会超过 |
| 批次状态 | 只升不降：运行中 < 中断 < 停下 < 调用上限用尽 < 暂停；原因记第一次升到这一级时的那一条 |
| 中断、服务停下（可以恢复） | 别的分身在各自的下一次规划调用前停住，现场保留，不记结局 |
| 程序错误（暂停） | 还没开始的分身记为未运行；正在过的分身照常过完（它们与出错的分身互不影响） |
| 进度文件 | 锁里写；`pending` 是每个分身一条"正在规划的年份"（取代原来的单个 `pending_clone`） |
| 归档库、付费账本 | 本来就是逐条事务写入（SQLite），线程之间安全 |
| Claude 命令行的进程环境 | 只在启动子进程那一下换成白名单环境（锁也只锁那一下），之后原样恢复；几个调用可以同时进行 |

## 恢复

分两步：先按名单顺序把每个分身已有的记录重放到需要新调用的地方，并要求归档里每条记录都被用到——这一步不写任何文件、不调用规划器，有冲突就拒绝；然后按 `workers` 继续。归档核对里"只有最后一次调用可以停在半途"改成每个分身各自一处（并行时几个分身可能同时停在半途）。
