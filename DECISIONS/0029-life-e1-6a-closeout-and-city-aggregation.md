>   就不能确定方向。硬要求单独报告。评价对照臂只改评价规格，不重跑生活。

## 一、所有者裁决（2026-10-12）

1. **撤回**"现金更多，V_reference 必须不下降"作为普遍验收要求。旧反例保留为历史证据；新测试检查"选择是否完整、是否尊重声明"。可以保留某个健康
   样例"增加现金后结果不变或变好"的事实测试，但不得把它宣传成一般定理。
2. **拆开**参考生活方案与治疗选择：先定义基础生活模板（岗位、住房、食品、服务、条件购买），医疗选择作为独立的估值分支（规则见第二节 F3）。
3. 先收尾、再在同一任务里继续 B；阶段一通过后不再等待所有者确认。
4. 城市统计口径：① 城市主要均值只用完成实际生活且 J 完整的分身；② 确认的生活出局不进均值、也不进模拟缺失范围，报告人数、比例与实际事件链；
   ③ 因资料、评分、反馈、执行支持或程序问题而不完整的分身留在原计划名单里，进缺失范围；④ 个别分身不完整不取消其他分身的有效结果；⑤ 不设置
   未经所有者决定的最低通过人数或缺失比例门槛，把实际人数与范围展示出来；⑥ 完成者均值不代表原计划全部分身或全部可能人生；⑦ 不增加"有积蓄
   让我安心"的奖励。
5. 模拟缺失范围的公式与两个手算验收例（10 人 → [0.45, 0.70]；部分记录 → [0.3, 0.8]）由所有者给定（第四节）。

## 二、A 收尾（审核 F1–F4）

**F1 结果身份必须与封存的实际生活一致。** 原表现：只把 `LifeYearResult` 外层的城市改成 B94（封存绑定、账目、分数原样），评价器接受，产出标为 B94
的完整 J；换分身编号、只有一年的部分轨迹也能归错。现在：`verify_trajectory` 在绑定指纹与账目核对之后，逐年核对外层的人、分身、城市、年份与封存的
`ScoredYear` 一致；评价器拿到的目录城市必须是封存生活的城市；年份顺序与相邻年份交接照旧核对；完整与部分轨迹同样核对。`CloneEvaluation` 的身份
与重复分身序号从封存绑定取；重新计算结果指纹不能把错标签变成合法结果。拒绝信息写明是第几份年度结果的哪个外层字段与哪份封存记录不一致。复用
已有的年度绑定，没有新的防伪机制。

**F2 已有物品不依赖商店是否继续出售新品。** 原表现：条件购买先查新品供给、再看是否已持有——家里有能用的洗烘一体机，新品缺货就把较舒适方案判成
不可行，新品资料未知就让 V / J 变空。现在：槽位绑定到一项明确的目录机会时先看估值期初持有，在服务期内就照用（不买、不重复付款、不重置寿命），
不要求新品可得或报价；没有才查供给、价格与资金。新品报价未知不影响照用旧的；旧物品的服务规格未知照常在评分里报未知。槽位"确定没有 / 资料
未知"（认不出是哪一件）照旧报告；不做跨品牌替代或物品匹配；到期物品不提供服务，也不挡正常购买。

**F4 运行入口与加载入口一致的配置检查。** 原表现：加载器能发现"健身服务槽位绑定到住房"，公开评价入口照样试算，最后混成"无法评价"。现在：按城
检查 `ledger.life_evaluation_config.city_binding_problems(spec, catalog)` 只有一份——加载器逐城调用，再做比较组层面的检查（城市集合、同一槽位
在各城的功能）；`evaluate_clone` 与 `value_terminal` 在任何试算之前经 `check_city_binding` 调用同一份，不通过就报配置错误；合法的"确定没有 /
资料未知"不受影响。没有大范围依赖重构。

**F3 拆开生活方案与治疗选择。** 原表现：较舒适生活被写死"条件允许就治"，没有同一生活下"不治疗"的选择；审核反例里期末现金 3,850 的 V 比 3,700
的低（钱多的人治了病，而对只看重交通、每月到岗 20 次的人，病假月分数反而更高）。现在（v2 / r2）：

* 评价规格写**基础生活模板**（`life_templates`，1–6 个，不含治疗选择）与治疗分支规则 `by_continuing_illness_v1`，二者进入内容身份；看结果前冻结，
  各城同一规则。
* 估值期初**健康**：每个模板一个分支，编号就是模板编号，治疗选择"未触发"；年度计划的应急安排写 decline 只为满足格式，不代表偏好；不重复
  计算两份相同的生活；最多 6 次试算。
* 估值期初**带病**：每个模板展开 `模板.treat`（只对正在延续的这场病写"条件允许就治"）与 `模板.decline`（不治疗）；不遍历未来疾病组合；最多 12 次
  试算。本样例 4 个模板（v1 的 p5"基本但不治疗"并入 p1 的不治疗分支），最多 8 次。**计算预算从"最多 6 次"变成"最多 12 次"。**
* 每个分支交给 E1-5C 结算：尊重 decline（现金够也不改成治疗）；治疗照旧受资金、时间、精力、供给与病程规则约束。
* 选择比较"模板 + 分支"；并列时按分支编号字典序展示（数值不变）；保留"有可能适用但无法评价的分支就不给 V"。
* 不根据医疗点数生成治疗选择，不调用 LLM。结果报告选中的模板与治疗分支及其生活后果；这是参考估值，不声称实际分身一定会这样选。
* 审核反例在 v2 下：钱多的人的不治疗分支重现钱少的人那份生活，两人 V 相同，钱多的人选中 `p2_current_comfort.decline`——这是这个例子的事实。

**另一处潜在缺陷（收尾时发现）**：旧代码给每个参考方案都写应急安排；E1-4B 到 E1-5B 的协议不允许写健康字段，在这些协议上估值会全部变成"输入
错误、无法评价"。现在只在带疾病规则的协议上写。

## 四、B：城市汇总

**汇总单位与名单。** 同一用户（偏好组）× 城市 × 重复分身序号。原计划名单（`RosterConfig`）声明比较组、用户与人、名单项（分身、完整城市身份、
重复序号）与运行臂（一个主臂、若干事先声明的评价对照臂）。ledger 的 `roster_problems` 只查名单本身说得通吗（偏好陈述、开局状态的人 / 城市 / 年份 /
重复序号、目录、比较组、各臂的城市绑定、**同一用户各城开局一致**——`common_start_digest`：现金、时间、精力与尺度、基础额度、能力、年龄、陈述的
职业、目标数、持有物的数量与剩余服务月；城市专属的编号不比）〔⚠ 2026-10-12 审核 R1：只比件数与剩余月数会把“健康 vs 已在生大病”“洗衣机 vs 手机”当成同一起点；已由第八节的标准开局 v1 取代〕；econ 的 `freeze_roster` 在跑任何生活之前记下内容身份（各臂的协议、评价规格内容
身份与执行修订、δ、H、N 与精确时间权重；各城目录与税绑定；各名单项的开局、共同开局摘要与评分输入），分类规则与范围规则的名字也冻结在里面。
名单为空或内部冲突整体拒绝。税绑定与评分输入的身份函数在 econ（`tax_binding_fingerprint`、`scoring_inputs_fingerprint`），所以冻结放在 econ；
ledger 不引用 econ。

**分类。** 每个名单项恰好一类：C（实际生活正常完成、实际评分完整、估值完整、`combined.status = complete`、J 非空且在 [0, 1]、核对通过）；E（`life_exit`
且出局原因是付不起最低住房与食品）；M（其余）。M 的原因按最早失败的环节：未运行 / 未返回（含只返回到中途）；计划或执行未完成（`plan_infeasible`，
或只因 `qualification_missing` 退回的输入错误）；资料缺失（`data_error`）；评分不完整；精力反馈受阻；E1-5C 停止；估值不完整或没有可用参考分支；
输入 / 配置 / 程序错误。`completed_scored` 不是 C 的充分条件。

**核对。** 每份结果重算指纹，身份（人、分身、城市；评价结果记下了重复分身序号时也核对序号）、运行臂（规格编号、内容身份、执行修订）、协议、目录与税、评分输入、第 1 年开局、实际月数、
时间权重与估值期长度都对照冻结名单。单项问题记为该项的 M（输入 / 配置 / 程序错误），不提取任何已知月份；同一项收到不止一份结果或失败记录也记为
M，不静默选一份；名单外结果单列拒收；运行失败记录（`RunFailure`：`contract` 输入或配置被拒绝 / `unexpected` 意外程序错误）归入该项的 M，意外错误
显式标出。评价对照同样重验两份报告的指纹与评价结果的指纹，不信改写过的对象。不要求各城目录或税绑定指纹相同。

**数值。** 全程精确分数。完整者均值 = Σ J ÷ C 与同一批 C 的 L、V 平均；出局比例 = E ÷ N；缺失比例 = M ÷ N；C = 0 时均值为空。M 项的
范围按第一节第 5 条的公式，K 与 W_known 取 E1-6A 已保存的逐月贡献与权重（核对不通过的项取 0），V 完整时上下界都用 V，否则 0 与 1；C 项取 [J, J]；
城市范围除以 C + M；检查 0 ≤ 下界 ≤ 上界 ≤ 1，矛盾报错。全员完整时范围退化为均值；全员出局时均值与范围都为空；名单为空拒绝；只有 1 个完整分身
时照给并注明。已知最好分支只作诊断，不当 V，不收窄范围。

**事件链。** 只从已核对的逐月事实摘要（E1-6A 新增的 `MonthFact`）、事件与出局 / 停止记录生成中文事实链，带年月与金额；停止不写成"看不起病"，
资料未知不写成"当地没有"；事件标签不互斥、不是因果贡献。

**硬要求。** 按名单项报告满足 / 违反 / 未知 / 只在生活过的月份满足；不删人、不扣分、不改出局；有违反或未知时城市报告注明。〔⚠ 2026-10-12：另写原计划人数、核验人数与未核验人数，见第八节〕

**城市比较。** 同一运行臂、同一用户：均值差（两边都有 C 时）与范围差 [A 下 − B 上, A 上 − B 下]；方向 `a_higher` / `b_higher` / `undetermined` /
`not_available`；出局比例与有效分身数一起写。不是显著性检验，不发布排行。缺失集中按城市、原因与显式给定的用户列出。

人数、L / V / J 的均值、范围与比较方向的变化及换类的原因；不覆盖主结果。H 只支持 12。〔⚠ 2026-10-12 审核 R3：“同一批实际生活”原来只比较传入的评价列表，列表可能不属于报告；已改为先按报告里的评价指纹配对证据，见第八节〕

**分层。** common：汇总契约、局部约束与内容身份（`common/life_aggregation_contracts.py`）；ledger：名单加载与跨对象检查（`ledger/life_roster.py`）；

中文报告（`scripts/demo_life_e1_6b.py`）；agentlayer：只把汇总侧的内部类型（`internal_aggregation_models`）与保留键（`RESERVED_AGGREGATION_KEYS`）
加进隔离登记。没有复制工资、税、时间、病程、评分或反馈公式；没有新依赖；没有 LLM 调用。
