## 一、要回答的问题

同一个用户的分身，在一座城市实际生活 N 年后，**过去过得怎样**，**留下的资源还能支持怎样的生活**？前者是实际体验（L_actual），后者是从真实终态
出发、按少量预先声明的参考方案在 12 个月估值期里真实结算与评分得到的期末估值（V_reference），二者按月份权重合成单分身的 J。钱、物品与资格不
直接加分，只通过估值期里实际买得起、用得上、做得了的生活起作用；没有"储蓄让我安心"的独立奖励。城市平均、出局事件链、缺失范围与城市比较
在 E1-6B。

## 二、所有者确认的评价口径（2026-10-11）

1. 确认生活出局的分身不进城市平均分；不作为未知分数放进缺失范围；保留全部已发生生活及实际事件链，B 轮独立报告；出局人数占比用原计划人数作分母。
2. 因模拟问题未完成计算的分身（资料缺失、评分不支持、反馈受阻、程序错误）与生活出局分开，不解释为生活差；B 轮纳入不确定性范围分析，不默认补零。
3. 部分分身停止不取消其他分身的有效结果；城市平均是"完成且评分完整的分身平均"，不宣称代表全部可能人生。
4. 现有 `stopped` 不自动改称生活出局：疾病之后应急安排不足、资源执行受阻或资料缺口，保留实际状态与原因；有疾病事件不等于证明了生活出局。

本轮实现单分身的分类与证据接口（第四节）；城市层面的统计留给 B。

## 三、实际生活：逐月汇总

* T = 12N，N 读协议的 `simulation_years`，代码里没有 36。逐月明细列满 T 个月，每个月写状态：`scored`、`incomplete`（这一年有评分但该月不完整，
  或这一年没有评分）、`exit_month`、`after_exit`、`stopped_month`、`after_stop`、`not_simulated`（轨迹在之前结束或这一年结算失败）。
* w_m = δ^(m−1)，W_actual = Σ w_m，L_actual = Σ w_m S_m ÷ W_actual。
* 精度：S_m 按评分器浮点数的最短十进制写法换成精确分数（复用 `econ.life_feedback.score_fraction`），全程有理数；显示值保留 6 位另存，不参与判断；
  不加 epsilon；金额照旧是整数最小单位；资源照旧是精确比较。
* 逐月汇总可能与"先对评分器的年度浮点均值再平均"只差最末一位（样例 u68：0.5370003886513797 与 0.5370003886513798）：来自评分器浮点求和的
  顺序。结果里写明原因，以逐月汇总为准，不为此改旧评分器。
* 只有 T 个月都 `scored` 才给 L_actual。部分轨迹保留已知月份、分数与加权贡献、缺失位置与原因、出局或停止记录、事件链与硬要求逐月汇总；
  不给 L_actual，不用已知月份平均冒充，不补零。
* 硬要求单独报告（逐需求统计满足、不满足、无法判断、没生活的月数），不进分数；实际生活里的硬要求失败不自动改成出局。

## 四、轨迹核对与分类（`econ/life_evaluation.py`）

**只认同一次受控运行。** `LifeYearResult` 增加一个私有属性：`run_life_year` 把它当场封存的年度绑定 `ScoredYear` 挂上去（不序列化、不参与
校验，已有输出逐字节不变）。评价器核对：

1. 每一年都带着封存的绑定，封存标记与对象指纹完好（复用 `ScoredYear.object_problems`）；结果里的账目与分数就是绑定里的那一份；
2. 协议、目录、税绑定、评分输入（规格、城市评分条件、偏好、硬要求）与评价器拿到的相同——产品陈述与研究真值不混用；
3. 同一人、分身、城市；年份从 1 起连续、不重复、不超过 N；
4. 第 y 年正式交接的状态正是第 y+1 年绑定里的年初状态；
5. **交接从封存绑定重新推出**：按同一份协议重算反馈记录（`econ.life_feedback.feedback_record`），用 `econ.life_year.handoff_from` 推出交接种类与
   交出去的状态，与结果对象对比——把终态换掉或把交接改个名字的复制品都被拒绝。`handoff_from` 是从 `run_life_year` 里提取出来的同一段逻辑，
   两处共用一份。

从 JSON 还原的结果没有封存绑定，明确拒绝："本轮不支持直接导入，请从保存的原始输入重放"。不为此扩建通用检查点或防伪系统。

**分类**（`TrajectoryRecord`，给 E1-6B）：

| 轨迹状态 | 来源 | 所有者口径（`owner_category`） |
|---|---|---|
| `complete` | N 年都正式交接，终态正常，T 个月都有合法评分 | `completed_scored`：进入城市平均（B） |
| `life_exit` | 最低住房与食品付不起而出局 | `life_exit`：不进平均、不当未知分数、比例用原计划人数（B） |
| `stopped` | E1-5C 停止（应急安排不足 / 资料缺口），原样保留种类与原因 | `stopped_kept_as_is`：不自动改称出局 |
| `score_incomplete`、`feedback_blocked`、`settlement_failed`、`not_finished` | 终态正常但有月份评分不完整；反馈受阻；计划或输入、资料错误；没跑完 | `simulation_incomplete`：不解释为生活差，B 做不确定性范围 |

事件链（`LifeEvent`）：发病、治疗、病假、出局、停止，带年月与说明。

## 五、期末估值上下文（`econ/life_terminal_value.py`）

只对正常结束（`complete` 或 `score_incomplete`）的终态估值；出局、停止、反馈受阻、结算失败、没跑完返回 `not_applicable`，估值器不复活它们。
估值入口检查：终态就是第 N+1 年的 `terminal`；有第 N 年的封存绑定；终态的健康部分确实由这份协议的疾病规则与事件来源产生。然后构造估值上下文，
记下每一项转换（`ValuationContext.conversions`）：

* **派生协议**：`simulation_years` N → N+1；事件来源换成派生的 `none`（流版本不变，说明文字不参与内容指纹）；其余原样。N 已到上限时拒绝。
* **估值年初状态**：`status` terminal → active；年份不重置；现金、能力、岗位记录、培训进度、资金目标、疾病与病史原样；已到期（剩余 0 个月）的
  持有物不带入，其余数量与剩余服务月不变；健康绑定的事件来源指纹改指派生来源，疾病规则指纹不变；额度见第八节。
* 派生协议与状态只在估值入口内；结果里只有它们的指纹与状态摘要（`ValuationStateSummary`：估值期初与各方案期末的现金、额度、持有物、能力、
  岗位、培训、疾病），没有可以拿去继续结算的状态对象，也不接回实际生活。

普通 `settle_year` 不变，照旧拒绝真实终态（`state_not_active`）；估值前后真实终态的指纹相同。

## 六、参考方案、槽位与选择

* **规格**（`EvaluationSpec`）：槽位（角色：岗位、住房、食品、服务、耐用品）、参考方案（1–6 个，编号唯一）、各城绑定（每座城为每个槽位写明
  绑定的目录机会、或"确定没有"、或"资料未知"并写原因）。方案里同一个槽位只能用一次，角色必须对得上。
* **加载检查**（`ledger/life_evaluation_config.py`）：协议要有月度资源规则与满足感反馈政策；绑定的城市就是评分配置比较组的城市，每座都有绑定；
  绑定的机会在那座城的目录里，结算角色与槽位一致（住房与食品按城市最低生活声明的合格名单认定）；同一槽位在各城绑定的机会声明同一组功能。
* **方案 → 年度计划**：岗位 `current_positions`（延续终态的当前岗位，可以没有）或 `qualified_alternative`（改做槽位绑定的岗位，资格按估值期初
  状态用 `qualification_gaps` 核对）；住房、食品、服务全年；条件购买 `buy_if_not_held`（期初已有在用的同一物品就不买）；应急选择由方案显式写。
  变成一份普通 `YearAction`（理由写明"估值专用"），用现有 `settle_year` 与同一份评分调用执行。不新开、不续学课程。
* **结果四类**：完整；已知不可行（资格不足、本城确定没有、估值期出局、计划不可行、方案里任何一项某个月因钱不够被拒）；违反已声明的硬要求；
  无法评价（资料未知——含"要治疗而本城治疗资料未知"——评分不完整、硬要求无法判断、偏好信息不足、输入错误、意外结果）。
* **选择**：没有无法评价的候选且至少一个完整 → `complete`，V_reference = 最高 V_p，并列时展示编号在前的方案（数值不变）；有无法评价的候选 →
  `incomplete`，不给 V_reference，`best_known` 只作诊断；全部已知不可行或违反硬要求 → `no_feasible_plan`。都不填 0，不把实际完成生活的分身改成出局。

本轮配置了五个方案：现职 + 基本、现职 + 较舒适（含条件购买洗衣设备与健身）、已具资格岗位 + 基本、已具资格岗位 + 较舒适、现职 + 基本但生病不治疗。

> ⚠ 本段的方案集合与"应急选择由方案显式写"已被 DECISIONS/0029 推翻，见该记录：v2 的方案是不含治疗选择的基础生活模板，治疗选择按估值期初健康状态展开成独立分支（健康：一个分支；带病：治 / 不治两个，最多 12 次试算）；原 p5 并入 p1 的不治疗分支。条件购买改为先看期初持有（F2）。

## 七、钱、物品、资格、课程、疾病、价格与目标

* 现金就是真实终态的余额，未来收支由现有账本结算；不额外造钱，不把余额换成分数。多留现金可以让原本付不起的方案变可行；全部可行之后更多现金不再
  提高有限期估值（饱和，如实报告）。
* 物品：数量与剩余服务月原样；不重置寿命、不重复付款；只有估值期实际提供的服务进入评分；不加转售残值；估值期之后剩下的服务月列入"未估值"。
* 资格：第 N 年完成、第 N+1 年起可用的能力可以支持估值期的相关岗位；职业、雇主与作用域照常核对；有资格不等于涨薪，只有方案实际执行岗位才有它的
  工资、税、工时与负担；不默认选最高工资；资格本身不重复给成长满足感（估值期不上课，没有成长项）。
* 课程：不新开、不续学；未完成课程不算资格；已付学费不退；这部分潜力列入"未估值"。
* 疾病：延续的疾病、已病月数与治疗历史原样，照同一套规则走完，不在入口痊愈；估值期没有新发疾病（确定性条件，不是把概率改成 0）；治疗由方案声明。
* 价格与环境：冻结的合成目录、税绑定、城市评分条件与评分规格；当地基年价；缺资料就报告，不补默认条件。
* 资金目标：不加分、不触发购买；估值中的购买不回写真实目标历史（估值状态不接回实际生活）。

## 八、估值期的精力额度

沿用实际运行的反馈开关、α、固定基础与量化：开着时用第 N 年完整年度满足感调用已有的 `quota_from_score`；关闭或 α = 0 时用基础值；第 N 年评分不完整
时额度无法确定，估值返回 `incomplete`（不补零、不沿用终态里第 N 年的旧额度）。额度只在估值上下文里，估值期内不再滚动更新，不用三年总分、估值或
J 计算。记录在 `ValuationQuota`（来源年份、基础、α、分数写法、未量化值、量化值、终态里的旧额度、政策与评分内容身份、第 N 年绑定指纹）。

## 九、合成 J

W_future = Σ_{k=1..H} δ^(T+k−1)；J = [Σ_m δ^(m−1) S_m + Σ_k δ^(T+k−1) S_future[选中,k]] ÷ (W_actual + W_future)。输出 L_actual、V_reference、J、
两部分的权重与份额、选中的方案与原因、实际与各方案的硬要求状态、未估值内容与假设。J 在 [0, 1]，不是货币，也不是"现实幸福的百分比"。实际分完整
而估值不完整时保留 L_actual，V_reference 与 J 为空并写明原因，不把 J 改成 L_actual，也不重新归一化。

## 十、内容身份与结果绑定

`EvaluationSpec.content_fingerprint` = 去掉 `spec_id`、`note`、方案标签与说明、槽位说明、绑定原因之后的规范 JSON 的 SHA-256，覆盖：内容格式、版本、
状态、执行修订、δ（按数值规范化）、H、估值事件条件、选择规则、合成公式、槽位与角色、参考方案、各城绑定（按城市排序）。同名不同内容就是另一个身份。
`CloneEvaluation` 绑定规格身份、协议、目录、税、评分输入、实际轨迹（各年年度绑定指纹）、终态指纹、估值上下文与各方案的计划 / 结果 / 分数指纹；
`result_fingerprint` 覆盖它的全部内容，重新校验时内容被改就拒绝；同样输入重放逐字节相同。不必为增加一个评价器更换实际生活协议：本轮没有改任何
既有执行语义。

## 十四、本地实现选择（prompt 没有写死，请所有者复核）

1. **"完整执行"按逐项、逐月判断**：方案里任何一项在任何一个月因钱不够被拒（例如健身月费某月付不起），整个方案判为已知不可行，不按"只执行了一部分"
   的生活评分。这样同一终态多给现金时，可行方案只会变多，V_reference 不会下降。代价：差一点点钱的方案直接出局，而不是"少去几次健身房"。
   > ⚠ 2026-10-12："V_reference 不会下降"作为一般承诺已撤回（所有者，DECISIONS/0029 第一、三节）——独立审核找到了反例（治疗写死在方案里时，钱多的人治了病、分数反而更低）。"逐项、逐月完整执行"这条规则本身仍有效。
2. **到期的持有物不带入估值期**（剩余 0 个月）：与普通年度交接对活跃状态的要求一致；它在估值期本来也不提供服务。
3. **第五个方案"现职 + 基本但生病不治疗"**：让"不花治疗费"的选择也在参考集合里；没有生病的终态上它与 p1 完全相同（并列，展示 p1）。
   > ⚠ 2026-10-12：已由 DECISIONS/0029 的治疗分支取代（每个模板都有不治疗分支；健康期初只执行一个分支，不再重复试算相同的生活）。
4. **期末延续的疾病遇到治疗资料未知**：年初的无事件试算已经包含延续的疾病，所以结算在年初就报资料缺口（`data_error`，什么都不提交），这个方案
   "无法评价"；估值期不会出现 E1-5C 的"停止"（万一出现，按意外结果无法评价）。
5. **第 N 年评分不完整时**：估值期额度无法确定，估值不完整；不改用基础额度。
6. **硬要求无法判断的方案归入"无法评价"**（不当满足，也不当违反），所以会让整个估值不完整。
7. **展示用的摘要字段**（估值期初与各方案期末的状态摘要、逐月健康状态、新发疾病次数）：为报告与测试可读而加，字段名避开可见对象的键名组合，
   不会被"原样序列化"的结构检查误判。
