## 一、所有者的要求（本轮 prompt 摘要）

原文见 [prompt 归档](../docs/design/prompts/2026-10-18-e3-a-input.md)。要点：实际贯通“原始答案 → 可读确认 → 已确认画像 → 标准初态及 E1 输入 → 现有检查与
冻结 → 三年离线生活 → E1 评价和汇总 → 产品结果”，至少一位用户跨两座合成城；六组模块（A 共享结构与样例，B 原始答案与精确偏好，C 六维接入 E1 与观察，

## 二、采用的规则

### 2.1 单一权威结构、版本与公共样例（模块 A）

* **唯一权威**：`src/common/product_contracts.py`（pydantic，冻结、拒绝多余字段）。`scripts/product_e3a.py export-schema` 导出 13 份 JSON Schema 与
  `index.json`（含每份的 SHA-256）到 `contracts/product/v1/`；`check-schema` 核对导出与权威结构逐字节相同、全部公共样例按结构校验、带出处标签与中文说明、
  不含本机路径或凭证。E5 从这里读取，不另维护一套业务模型；没有引入 Web 框架。
* **13 份消息**：`ProductCapabilities`、`UserInputDraft`、`ProfileReview`、`ConfirmedProfile`、`ProductPreflight`、`RunSubmission`、`RunReceipt`、
  `RunProgress`、`ProductResult`，以及资料与目录覆盖的 `SourceFact`、`OpportunityCandidate`、`CatalogCompilation`、`OptionInventoryCoverage`。
* **共同元数据**（`ProductMeta`）：结构版本、问卷版本、词表版本、健康问卷版本、转换版本、资料包身份（编号、状态、内容指纹）、样例出处标签。错误统一是
  `ProductIssue`：机器代码、字段位置、中文原因、影响、下一步动作与严重程度。
* **样例出处标签**（`SampleLabel.origin`）：`offline_run`（真实代码路径离线生成）、`controlled_fixture`（受控夹具，例如注入一次大病）、
  `contract_example`（标明为示例的契约响应，例如线上查询接口，**不是已实现的 API**）；全部 `synthetic: true`。35 份公共样例由
  `scripts/product_e3a.py samples` 用真实代码重新生成，两次在新临时目录重新生成与仓库里的文件逐字节相同。
* **线上服务留 E3-C**：提交、幂等与进度查询在本轮只有本地离线桥接（`service: offline_bridge`，幂等登记在本地目录）与标明为示例的响应；不能把样例称为已实现的
  托管 API。

### 2.2 原始答案 → 可读确认 → 已确认画像（模块 B）

* **三层分开保存**：`UserInputDraft`（照用户填的写，逐项状态）→ `ProfileReview`（可读解释、职业候选、缺失、未支持项、待确认内容）→ `ConfirmedProfile`
  （已确认语义、精确数值、来源与内容身份）。四种状态分开：答案（未答 / 已提供 / 明确无所谓 / 暂不确定）、支持（支持 / 部分支持 / 未支持）、确认
  （待确认 / 已确认 / 修改后失效）、用途（规划 / 初态 / 资格 / 评分 / 仅留存；硬要求另标“执行不保障”）。
* **定和分配**：规则见“当前规则一览”。合计不是 100 时报 `points_sum_not_100`，写明差多少，不按比例扣减或补齐；超过 100、格式不对（`points_not_a_number`、
  `points_too_many_decimals`、`points_fraction_not_canonical`）、选了均分又填了数（`equal_split_with_values`）各有代码。正权重缺资料或没有评分分项时
  在预检查里报告，不静默删掉再重新归一化。
* **旧键**：六维里出现 `healthcare` 报 `healthcare_not_in_six_dimensions`（不会改读成健康回答）；物质里出现 `laundry` 报 `legacy_laundry_key`
  （旧“洗衣”问的是有没有洗衣条件，不能当作“日常生活便利”），都需要用户按新题重新分配。
* **健康问卷**：三道暂定题（题干与共同提示照 prompt 原文），选项“符合我 / 不符合我 / 无明显倾向 / 暂不确定”，无预选；未答另存。保留题目版本、题目 ID、
  答案状态、选项及含义；不算总分，不推断患病概率、疼痛权重、疗效、愿付金额或拒绝治疗。未答与暂不确定在观察里写明“没有这一项的明确指令”。
* **职业**：受控词表（概念 → 别名 → 各国分类映射）与明确的别名匹配规则 `controlled_vocabulary_alias_match_v1`；明确、歧义（给少量可读候选，不展示代码）、
  未知三条路径都实现。内部保留国家、分类体系、版本、代码与依据（SOC 2018 代码只用于演示内部保留方式）；职业、资格与城市岗位分别记录，不从职称授予资格；
  不新增招聘概率。
* **金额**：保留原始数额、币种、时期与口径（`liquid_funds_v1`）；只有资料包登记了的口径才能换算（本版只有 `USD / 2024 → USD_2024_LOCAL` 恒等换算），
  “当前 10,000 美元”这类没有合法依据的口径报 `money_conversion_missing` 并阻断。
* **文字与属性**：自由文字最多 2,000 字符，超限报 `free_text_too_long`，不截断；不调用 LLM 提取，不沿用旧文本调分。品牌、菜系、制作方式、档次、服务质量
  与上门顾虑保留原文与“未支持、仅留存”；用户把“不让陌生人进家”标为不可妥协时报 `hard_requirement_not_enforceable`（本版没有能拦截上门服务的机制），
  不伪称硬要求检查能保障。受支持的硬要求只有“住处到就业中心的往返分钟上限”（编成 E1 的结构化硬要求，单独报告，不进分数、不拦截计划）。
* **访谈接口保留**：证据引用 `EvidenceRef.kind` 有 `form_field` 与 `interview_turn_reserved`，字段来源 `FieldSource` 记每个确认字段来自哪里；本轮只有表单入口，
  不实现访谈，不把 MBTI、塔罗等标签映射成数值或事实。

### 2.3 六维接入 E1（模块 C）

* **新类型与新来源**：`common.life_product_profile.ProductLifeProfile`（六维与物质的精确点数、物质状态、独立健康回答、硬要求、文字与属性）；偏好来源
  `product_confirmed_six_dim`。协议的健康输入声明新增 `IndependentHealthInputDeclaration`（`kind: independent_health_answers`、语义
  `independent_health_answers_v1`、问卷版本、用途 `agent_planning_information_only`）。
* **只转一次**：`econ.life_scoring.preference_from_confirmed_profile` 用精确分数算 点数 / 100，最后只转一次浮点，得到 `ScoringPreference`
  （`dimension_weights` 只有六维）；`effective_weights` 对这个来源直接返回六维权重（只允许健康评分版本，否则拒绝“补一个医疗占位分”）。因为六维合计 100，
  这正等于旧路径的 w̃_k = w_k / Σ_{j≠healthcare} w_j；之后的分项、B = Σ w̃_k s_k 与 S = (1 − γ)·B + γ·H 原样复用。内部的 `HealthWeighting` 记下
  “来自独立健康回答”，不再伪造一份七维原始权重。
* **显式分派**：`econ.life_year.PREFERENCE_INPUT_TYPES` 是偏好来源 → 输入类型的对照表（旧七维陈述、研究真值、六维产品画像）；不认识的来源或类型报错，
  不落入“否则就是研究真值”的旧分支。六维画像必须配独立健康声明且问卷版本一致；旧类型配独立健康声明被拒绝。
* **完整路径的检查**：生活输入加载（`LifeBundle.product_profiles`，与旧画像同人不能并存，不能把七维医疗点数改读成独立健康回答）、评分配置（物质三项与
  便利版本）、名单冻结与标准开局（两种画像都接受，个人条件核对不变）、运行配置（模板与协议配套；六维画像的运行必须显式写 `show_health_answers`）、
  观察构造、年度调用、覆盖（经 `effective_weights`，`life_coverage.py` 不需要改）、评价身份与归档绑定（画像的身份进入评分输入指纹与年度绑定）。
* **派生产品协议**：`life-v1-e3a-product` 与便利版的生活规则、资源、职业、储蓄、疾病规则与评分规格内容相同，只换健康输入声明、反馈政策的偏好来源与编号；
  评分规格只把 `protocol_id` 指向派生协议，内容身份不变。

### 2.4 标准开局与金额

编译器为每座候选城、每个重复序号生成一份第 1 年开局：健康、没有已有物品、病史、在学课程与结构化储蓄目标；年龄、现金口径与数额、能力、基础时间
（4,380 小时/年）与精力额度（250 负担点/月）对同一用户相同；当地岗位按目录里与确认职业同一分类的岗位匹配（多份时取编号最小的那一份），匹配不到报
`start_job_unmatched`，岗位要求未确认的资格报 `start_job_requires_unconfirmed_ability`，都不自动换职业或授予资格。之后照常经过 E1 的
`ledger.life_roster.roster_problems`（标准开局 v1 与跨城个人条件）与运行前检查；往开局塞旧设备等非法状态由 E1 拒绝，预检查报告阻断（内部路径隐去）。
时间与精力是本版统一的模型设定，用户不填负担点数。

### 2.5 规划观察、提示模板与 mock

* **观察**：`AgentObservation.profile` 对六维画像显式投影六维精确点数、物质分配与状态、独立健康回答（题目、答案状态、含义与“给分身的读法”）、软偏好、
  硬要求与文字；新许可 `show_health_answers` 对产品画像**没有默认值**（运行配置与观察构造都要求显式写）；不允许看的部分列在 `not_permitted` 里，
  而不是悄悄缺失。研究真值、评分参数、评价结果与隐藏风险关系照旧不进观察。
* **提示模板** `e3a-product-prompt-v1`：系统提示、用户开头与输出格式与 `e1-7b-prompt-v1` 逐字相同；行动说明书 `e3a-product-action-guide-v1` =
  开头多一节“你的用户陈述：六维、物质分配与独立健康回答”（只讲字段含义：精确分数写法、物质分配不是预算、健康回答独立且不是治疗指令、未答与不确定
  没有明确指令）+ 便利版的全部各节。旧模板 `e1-7b-prompt-v1`、`e1-convenience-prompt-v1` 的请求逐字节不变；模板兼容声明扩展、检查不删。
* **mock** `e3a-product-mock-rules-v1`（`ProductMockPlanner`）：复用便利版的方案选择（读观察里的精确点数）；应急安排改为**固定测试政策** M6p——小病、
  大病都写 `treat_if_possible`。这是 mock 的测试设定，**不是**从健康回答推断出的治疗态度；没有 healthcare 点数也不会因此默认不治疗；健康回答只出现在
  需求摘要里，不改变任何行动。旧 mock 规则（`e1-7a-mock-rules-v1`、`e1-convenience-mock-rules-v1`）不变。

### 2.6 便利资料候选、合法目录与选项目录覆盖（模块 D）

* **三层**：`SourceFact`（原始值、单位、时期、地理、来源性质 observed / derived / estimated / synthetic、换算或假设）→ `OpportunityCandidate`
  （设备或服务的逐字段状态：报价、寿命、效果、本人参与、供给）→ `CatalogCompilation`（编入的 E1 机会、未编入的候选与原因、版本、范围与来源映射）。
* **编译规则**（`product.catalog`）：报价必须与目录同一口径（币种、基年、当地基年价），设备一次付款、服务按月付款；按次上门报 `billing_unit_unsupported`，
  不换成月套餐；寿命必须是明确的 1–30 整数年并写生效时点（未知 `lifetime_unknown`、非整数 `lifetime_not_integer`、越界 `lifetime_out_of_range`，
  不补值、不取整）；效果未知报 `effect_unknown`，不删替代字段伪装成“确定没有效果”；残余小时必须在 0 到全组共用基准之间（`residual_invalid`），
  任务必须是协议声明的代表性杂务；服务的本人参与时间未知报 `participation_unknown`（不当 0）。报价未知而其余齐全时编成 `availability: unknown`
  （E1 其余结构约束照旧满足）。编入的机会按所用事实里**最弱**的来源性质标注（真实报价 + 假设效果仍是假设）；有卖但寿命未知不改写成确定买不到。
* **编入目录**：编译出的便利设备与服务替换便利版目录里原有的那几项，其余机会原样。服务资料适用期、计划月份与实际服务月份分开，实际月份由 E1 结算产生。
  每项任务取最小残余、设备寿命、服务实际覆盖月份、便利分与期末估值模板全部沿用 E1。
* **选项目录覆盖**（`OptionInventoryCoverage`）：声明范围与版本（`e3a-convenience-inventory-scope-v1`：只调查能替代洗衣或打扫的设备与人工服务）、被调查的
  类别与候选、已解决 / 未解决 / 排除及原因、`complete_for_declared_scope / partial / not_assessed`，并说明不保证穷尽整个城市市场；排除项与未知项都留在分母里。
  轨迹可评分、选项目录覆盖与分身 C / E / M 是三件不同的事：没有采用方案且资源账完整时便利分是 E1 确定的 0；缺实际资源记录则未知；目录缺口不改写已发生轨迹的评分。
* **E3-B 的接入口**：真实资料只需要产出 `SourceFact` 与 `OpportunityCandidate`，经同一个编译器进入 E1；美国资料的必要来源、字段、尺度与缺口盘点见技术说明
  第 8 节（只是盘点，不是抓取管线；`scripts/fetch_data.py` 仍是占位）。

### 2.7 离线桥接与产品结果（模块 E）

* **预检查**（`product.preflight.run_preflight`）：确认身份核对 → 编译 → E1 运行前检查（复用 `orchestration.life_runner.preflight`：名单冻结、标准开局、
  配置与事实核对）→ 覆盖报告（`econ.life_coverage.coverage_report`）→ 逐城与总体的“可执行 / 可评分 / 可反馈”（只描述当前输入与声明范围，不保证未来每份
  计划合法）、开局摘要、资料缺口、人数与年数、规划器与费用上限、运行绑定（编译产物、协议、评分内容身份、评价、提示模板、规划器与运行清单身份）。
  任何一步不通过都是 `blocked` 并附原因，不删城市或分身。
* **提交**（`product.bridge.submit`）：引用确认与预检查的身份、带幂等键；运行编号由幂等键与预检查身份决定；同一幂等键、同一预检查的重复提交返回原运行
  （`duplicate_same_run`），同一个幂等键已经用于另一份预检查时被拒（`idempotency_key_reused`），确认或预检查对不上、确认已失效、预检查过期被拒
  （`submission_confirmed_mismatch`、`submission_preflight_mismatch`、`confirmation_invalidated_by_edit`、`preflight_stale` 等）。本地登记只是离线等价物，
  持久幂等与托管服务留 E3-C。
* **运行**：`product.bridge.run_offline` 只接受 mock 规划器，调用已有运行器：每分身每年 1 次规划、最多 2 次修订、有限的事实记忆、归档与零调用重放全部沿用；
  编译产物用相对路径，输入完整冻结进归档（`replayable_from_snapshot: true`）。
* **结果**（`product.results`）：从 E1 报告做白名单投影——C / E / M 与 N = C + E + M、完成者均值（分母 C；C = 0 时为空）、模拟缺失范围（分母 C + M；
  全 E 时为空）、L / V / J 的精确分数与显示值、事件链（取自核对过的环境记录）、硬要求的已核验 / 未核验人数、城市比较（E1 的范围差，不是显著性检验）、
  逐年生活事实（实际支付、在用设备、实际服务月份与没买到的月份、住房与食品、每月家务小时、病情月份）、选项目录覆盖、来源与限制。服务或预算暂停而没有报告时
  `evaluation_status: not_generated`，不擅自分类。结果里没有评分参数、内部对象、模型理由或本机路径，也不回灌给仍在生活的分身。

## 四、本地实现选择（prompt 没有写死，请所有者复核）

1. 手工输入最多 2 位小数、显示 1 位小数、显示用四舍五入（ROUND_HALF_UP）；规范分数是约分后的“整数”或“分子/分母”。
2. 职业匹配：别名在原文里出现即算命中；恰好一个概念命中是明确，多个是歧义（列出候选让用户选），没有命中是未知；用户也可以直接选一个候选。
3. 金额只开放“2024 年美元、当地价格水平”这一种恒等口径（与合成目录同一口径）；任何换算都要等 E3-B/C 的真实资料与依据。
4. 产品运行默认让分身看到健康回答（资料包的运行设置 `show_health_answers: true`）；许可字段本身没有默认值，研究对照可以显式关闭。
5. mock 的应急固定为“能治就治”（M6p）：这只是让离线闭环可执行的测试政策，不代表任何用户的治疗态度。
6. 编入的便利机会替换便利版目录里的原有那几项（资料包用的是同一组合成报价与效果；离线闭环里 K51 买设备包、M52 按月买杂务服务，与便利版 mock 的选择
   方向相同）；来源性质取所用事实中最弱的一种。
7. 每城一个分身（重复序号 0）、三年；全局调用上限 = 分身数 × 年数 × 每年候选上限（3）。
8. 硬要求本版只开放“往返通勤分钟上限”（E1 已能逐月核验的那一种）；其余写成未支持、仅留存。
9. 运行编号 = “幂等键 | 预检查身份”的 SHA-256 前 16 位；幂等登记是调用方指定目录里的一个本地文件（只是离线等价物）。

### 9.1 F1：产品规则代码进运行身份

* **根因**：运行清单的关键源码清单（`life_runner.KEY_SOURCES`）没有 `common/life_product_profile.py`，而它的 `dimension_fractions()` 实际决定评分权重；
  在隔离副本里交换物质与安全的读取，身份不变、恢复照样执行了一年。
* **修复**（`orchestration/life_runner.py`）：名单里有六维产品画像的运行，运行清单另记 `source_set: e3a-product-sources-r1` 与
  `source:common/life_product_profile.py`；旧协议、旧输入的运行清单一个字段都不多。恢复与重放先单独核对这一项：运行清单写了不认识的版本 → 拒绝（不退回较弱的
  旧检查）；当前是产品运行而运行清单没有 `source_set` → 判定为修复前的产品归档，拒绝并说明原因与重新运行方式；之后照旧逐项比较全部身份。
* **绑定边界**：只记运行时把画像变成评分输入的代码。偏好转换（`econ/life_scoring.py`）、观察、提示与 mock 本来就在 `KEY_SOURCES`；产品层的审阅、编译与
  资料编译只产生冻结进归档的输入文件（它们一变，冻结输入、协议、目录或名单的身份就变）；结果投影在生活之后，不影响运行语义。没有把整个仓库加进指纹。
* **兼容**：历史读取（直接读归档 JSON）照旧；旧版核验与零调用重放用创建归档时的源码快照（修复前的 E3-A 源码保存在
  `runs/2026-10-18-e3a-closeout/historical_source/src/`，实测能零调用重放 `runs/2026-10-18-e3-a-input` 的正常闭环归档）；用现在的代码续跑修复前的产品归档被拒绝，
  归档原样保留，要继续就用归档冻结的输入以新的运行编号重新开跑。

### 9.2 F2：缺来源、缺单位或非法数值不能升级成“资料齐全”

* **根因**：编译器只检查字段有没有值，不检查来源与单位：没有来源时自动生成没有依据的合成说明，计价单位缺失时补默认值，参与时间的非法数值直接抛异常让整批
  失败；覆盖报告把供给未知写成报价未知、把确定不可得记成未解决。
* **修复**（`product/catalog.py`，编译器 `e3a-catalog-compiler-v2`）：每个实际用到的已知字段都要有来源事实——存在、记录的就是这个字段（跨字段推导本版没有登记
  任何方法）、单位对得上（报价用资料包的当地基年价口径、寿命用年、效果与参与用 小时/月）；报价与寿命还要有一条事实的原始值等于它，或是写明换算方法的派生 /
  估计事实。合成事实本身必须写假设说明（`SourceFact` 校验），所以合成路径只在假设真实登记并被引用时可用。计价单位缺失 `price_unit_missing`；参与小时或负担不是
  不小于 0、最多两位小数的数 `participation_invalid`；来源问题 `source_missing` / `source_unknown_fact` / `source_field_mismatch` / `source_unit_mismatch` /
  `source_value_mismatch`。都是逐候选的结构化原因，其余候选照常编译；编出的机会再通不过 E1 的 `LifeOpportunity` 校验就是程序错误，原样抛出。
* **状态分开**：覆盖条目新增供给状态（有卖 / 确定没有 / 不知道）、资料状态（齐全 / 只缺报价 / 有缺口 / 不需要 / 不在范围）与编译状态（可购买 / 资料未知 /
  未编入）；编入的资料未知机会写明原因（报价未知 / 供给未知 / 两者都未知）。确定不可得是已确定的调查结果（计入已解决），但不是可购买方案。分母仍是过滤前调查
  过的全部候选。资料包里报价未知的烘干机补写了计价单位（以前靠默认值）。不改 E1 的便利公式、确定的 q = 0、轨迹评分或 C / E / M。

### 9.3 F3：金额严格解析

* **根因**：解析前无条件删除逗号，`3000,50` 成了 300,050 美元，`3,,000` 也被接受。
* **修复**（`product/exact.py`，转换版本 `e3a-conversion-v2`）：只接受不分组的非负十进制（`3000.50`）或严格每三位一组的千分位（`3,000.50`），小数点只用“.”；
  其余拒绝并返回机器代码、字段 `cash.amount_text` 与中文纠正说明（`money_separator_invalid`、`money_negative`、`money_too_many_decimals`、
  `money_not_a_number`）。确认后的金额保留原文、数值含义不变；能力清单新增 `money_input_rule_zh` 告诉 E5 这条规则（前端提示不代替服务端检查）。

### 9.4 F4：重复或冲突答案在确认前拒绝

* **根因**：审阅按字典收集答案，同一健康题后者覆盖前者；资格出现一次“已提供”就算持有；两条通勤上限都通过审阅与确认，到编译时才抛未捕获的 ValidationError。
* **修复**（`product/answers.py`、`product/compile.py`）：审阅按健康题编号、资格编号、硬要求编号以及受支持选项对应的 E1 需求检查重复；重复一律拒绝（包括完全
  相同的），不按最后一个算、不按“出现一次就有”、不自动取更严格的上限（`health_answer_duplicated`、`ability_duplicated`、`hard_requirement_duplicated`、
  `hard_requirement_conflict`）；提示内容与提交顺序无关。编译时若确认画像仍违反 E1 画像契约（例如别处构造的画像），转成结构化拒绝
  `profile_contract_rejected`，原文写进编译目录的内部诊断，不吞掉也不让异常逃出预检查。未答、明确 0、无所谓、暂不确定的语义不变。

### 9.5 F5：公开错误白名单

* **根因**：产品结果直接透传 E1 名单项的 `detail`，进度直接透传 `pause_reason`，预检查用正则删路径后透传 E1 的拒绝原文——异常里的路径与任意内部文字都会出现在
  公开响应里。
* **修复**（`product/public_errors.py`、`product/results.py`、`product/bridge.py`、`product/preflight.py`）：分身说明（`CloneResult.explanation`）、批次暂停
  （`RunProgress.pause`）与预检查拒绝（`ProductIssue.audit_ref`）只由结构化类别生成——类别代码、中文原因、影响、下一步，加不含内部内容的审计编号（运行编号 /
  分身 / 记录文件，或内部诊断编号）。E1 的每一种 C / E / M 原因与批次停下原因都登记了公开说明，没登记的类别直接报错，不退回显示原文。完整原文留在运行归档
  （`failures.json`、`progress.json`）或编译目录的 `diagnostics/`。暂停的含义、报告是否生成与 C / E / M 分类不变。删掉了原来的路径正则。

### 9.6 版本与兼容

| 项目 | 变化 | 原因 |
|---|---|---|
| 共享结构 | `e3a-product-schema-v1` → `v2`；导出到 `contracts/product/v2/`（v1 目录原样保留为历史导出） | 新增或替换了字段：`ProductIssue.audit_ref`、`PublicExplanation`、`CloneResult.explanation`（替换 `detail_zh`）、`RunProgress.pause`（替换 `pause_reason`）、覆盖条目三种状态、`CompiledOpportunity.unknown_reason`、`ProductCapabilities.money_input_rule_zh` |
| 转换 | `e3a-conversion-v1` → `v2` | 金额写法规则变了；旧确认要重新确认（结构版本变化也会让它失效） |
| 目录编译器 | `e3a-catalog-compiler-v1` → `v2` | 来源、单位与状态规则；编入的机会 `mapping_version` 随之变化，目录身份因此不同 |
| 产品源码身份 | 新增 `e3a-product-sources-r1`（只在产品运行） | F1 |
| 不变 | 问卷、词表、健康问卷、产品画像、偏好来源、健康输入声明、派生协议、提示模板、mock 规则、评分内容身份 | 语义没有变 |

正常闭环的生活数值不变（同一用户、两座合成城、三年：L / V / J、逐年生活事实与家务小时与修复前逐项相同，见证据 `normal_loop/`）；运行编号、目录与协议的内容身份
因版本变化而不同。旧协议、旧输入与旧归档的核对照旧（7 个旧路径场景比较，见证据 `legacy/`）。

### 9.7 仍然存在的限制

审核的非阻塞建议（旧 mock 与六维画像混配的配套检查、线上提交更早识别陈旧预检查）没有纳入本轮。来源检查确认的是“有登记的来源与单位”，不判断来源本身是否
真实可靠；合成资料包仍是合成。公开说明是按类别的通用文字，具体原因要维护者按审计编号查内部记录。
