1. 目标与范围
我们已经决定尝试用 LangGraph 组织产品运行流程：
已确认画像
→ 调用 E3 运行前检查

→ 幂等提交
→ 启动或恢复已有 E1 模拟
→ 通过 E3 投影进度和结果。
生活含义：用户确认“按这些个人条件、城市资料与模拟设置开始”，关掉页面或程序后仍能接着查看；重复操作不能再生成一批分身，或重复支付规划费用。

4. 最小实现
A. 使用真实 LangGraph
使用当前兼容的 LangGraph 与必要的本地持久化依赖，按仓库依赖管理方式锁定实际版本。
采用明确的 StateGraph。用能够跨进程重启读取的本地 checkpointer；SQLite 等轻量方案即可，不能只用内存演示恢复。
不要求 LangSmith 或外部托管平台，不开启外部追踪上传。不要为本轮更换现有模型客户端。
B. 外层状态只保存流程信息
保存：

* workflow_id / LangGraph thread_id；
* 已确认画像、资料包、预检查和配置的引用及内容身份；
* 当前阶段与待确认事项；
* 稳定的幂等键；
* E1 run_id、归档引用、结果引用；
* 流程版本及必要的兼容信息。

钱、病情、资格、年度评分等仍由 E1 归档负责。不要在 checkpoint 中再维护另一份可独立修改的生活状态，也不要通过普通字典反序列化绕过已有年度封存检查。
thread_id 表示一次外层流程，不是用户身份或访问权限。一条已提交流程绑定一个 E1 运行；不得在恢复时悄悄换 run_id。
C. 用户确认
原型从已有 ConfirmedProfile 开始，不重做输入问卷。
调用 E3 预检查，展示本次范围与限制，再等待明确确认。确认绑定这份预检查的内容身份；修改画像、城市、资料、政策、模型或预算后，必须重新检查并确认。
用户尚未确认或拒绝时，不调用规划器、不启动 E1。等待确认的节点保持简单，避免把不可重复的写入放在 interrupt 前。
用户对画像的确认和对“开始这次模拟”的确认是两件事；不要在同一次运行中无意义地反复确认。
D. E1 启动与恢复适配
现有 bridge.submit 只登记运行，bridge.run_offline 则直接 start_run。不能把后者原样放进一个可能重跑的节点。
实现一份小型适配器，依照已有记录选择：

1. 尚未启动：调用原有启动入口。
2. 已在 E1 支持的边界中断：调用原有恢复入口。
3. 已完成：只读核对并返回已有结果。
4. 发送状态不确定、身份冲突、预算阻断或归档不一致：保留原状态，返回需要处理的原因。

重复提交使用同一个幂等键和运行 ID。恢复不得清零预算、候选次数或服务历史，不得重新询问已经保存合法回复的年度。
E1 已完成、LangGraph 尚未写下完成 checkpoint，是必须处理的情况：此时不能重新模拟一次。
部分初始化、映射冲突或损坏归档不能靠删除目录、猜状态或新建运行“恢复成功”。
E. 两层各管什么

* LangGraph：预检查、确认、调用运行、等待处理、结果交付。
* E1：分身调度、年度候选、重试、执行、预算与真实运行进度。
* E3：公开进度与结果投影。

不要增加第二套自动模型重试；不要用 LangGraph 的自动重试包住有副作用的整个 E1 节点。
本轮串行、单执行者。年度内部的恢复能力仍以 E1 已支持的边界为准，不宣称任意指令位置都可恢复。
F. 产品展示与信息边界
进度和结果通过现有 E3 投影产生。前端未来不会直接读取 graph.get_state、checkpoint 或内部异常。
流程阶段与生活结果分开：

* 外层结束，不代表每个分身都正常完成；
* E、M 不互换；
* 结果尚未生成，不补零、不虚构城市分类；
* 隐藏评分参数、研究真值、密钥、本机路径不进入公开响应。

本轮提供独立的本地演示入口，不切换旧 CLI 默认配置。新产品演示使用 E3 生成的便利版整套输入，不能只更换物质偏好字段。
5. 验收
先完成针对性检查，再跑完整离线回归。所有真实调用保持为 0。
至少证明：

1. LangGraph 真正执行了预检查、确认、运行和结果投影；持久化后换一个进程仍可继续。
2. 未确认、拒绝确认、过期确认均不会启动规划。
3. 相同输入重复提交返回同一运行；同一幂等键携带不同输入被拒绝。
4. “提交已经登记、checkpoint 尚未更新”后恢复，不生成第二个运行。
5. E1 在已有支持边界中断后，由原恢复入口接上；已保存回复不重复调用。
6. “E1 已完成、外层尚未记完成”后恢复，只核对和读取已有结果。
7. 重复确认、重复恢复和重复读取结果，不重复执行年度。
8. 配置变更、错误归档、映射冲突在执行前被拒绝；失败核对不改写原始证据。
9. 现有预算与发送不确定状态不会被外层自动重试绕过。使用离线故障注入验证，不能真实花钱制造错误。
10. 同一冻结输入、同一 mock 行为或固定回复，直接路径与 LangGraph 路径的行动、现金、病情、资源、评分、L/V/J、C/E/M 和公开报告精确一致。
11. 正常、生活出局、模拟问题与暂停均能正确投影；公开失败信息不泄漏内部异常。
12. 公共结构及样例仍通过 E3 的契约检查，旧直接入口保持可用。

精确比较不加容差。新增流程身份、时间戳等预期差异须在比较前按字段列明，不能用大范围忽略掩盖业务差异。
关键的防重复执行和身份检查需要有真正能失败的反例。若做变异检查，只在临时副本运行，记录实际发现，不能修改工作区或旧证据。
6. 文档和交接
新增一份易懂的流程说明，例如：
docs/design/langgraph-product-workflow.md
至少写清：

* 流程图与一个用户故事；
* LangGraph、E1、E3、E5 各自职责；
* 如何启动、确认、查询、恢复；
* 已验证的中断位置与仍不支持的情况；
* 公共接口与内部状态的区别；
* 依赖版本、关闭新入口后如何继续使用旧入口；
* E3-C 与 E5 接下来应调用什么。

根目录导航只做必要更新。共享契约文件与双方交接说明由 E3 主责；给它一份具体同步清单，不同时各写一套。
证据放新目录，包含实际命令、结果、对照与复现入口。不要重写历史报告。
7. 中文反馈要求
按以下顺序向所有者汇报，面向大四统计本科生：

1. 结论：实现了什么，哪些仍只是原型，是否待独立复核。
2. 一个完整故事：用户确认 → 模拟 → 关闭程序 → 恢复 → 看结果。
3. 两个故障故事：重复提交、模拟完成但外层中断，分别为什么不会重跑。
4. 一张职责表：谁管流程、生活、预算、接口、界面。
5. 直接路径与新路径哪些数字完全相同，哪些只是身份或记录变化。
6. 实际运行的检查、没有运行的检查、发现并修复的问题分别列出。
7. 给 E3、E5 的具体交接入口与剩余依赖。

不要只汇报“测试全部通过”，也不要宣称“换上框架就支持生产并发或绝不会重复收费”。
完成后停在独立审核点，不自动开始真实 API 试跑、真实数据接入或前端建设。
