三、已经确认的规则
1. 时间：精确核算，允许未安排部分月底作废
继续使用精确有理数计算时间和负担：

* 活动使用量等于预算时允许；
* 超过预算时不允许；
* 不添加容差，不先舍入再决定是否超限。

但不要求活动必须把预算用满：

```
已安排时间 + 未安排时间 = 当月时间预算
已安排时间 ≤ 当月时间预算
```

未安排时间：

* 当月结束后作废；
* 不自动解释为休息；
* 不恢复精力、不增加满足感；
* 不结转，不跨月借用。

可以继续使用已有 `time_remaining` 字段，但面向人的说明必须明确：“未安排时间，月底作废”。不要为了表达这一点增加无必要的重复字段。
已预留的睡眠、基本生活时间不重复进入活动账。
2. 精力：月度可承受负担额度
允许继续复用 `energy.level`，新协议中明确表示“月度可承受负担额度”，由尺度版本区分旧含义。

* 它不是随活动扣减、随休息恢复的体力电池。
* 剩余额度不结转。
* 本轮同一个人的基础额度不随城市、月份或年份自动改变。
* 满足感不改变额度。
* 时间约束与精力约束分别检查。

四、F1：出局月仍须检查已知劳动的资源下限
已复现的问题
合法远程兼职需要每月 80 小时、80 负担点：

* 开局现金 0；
* 月工资 1,000；
* 最低住房和食品 1,380；
* 月时间预算或精力额度设为 60。

当前程序返回 `exited`，保留工资和对应劳动，却不检查 80 是否超过 60。
同一份超负担劳动，增加初始现金后反而会被判为 `plan_infeasible`。资金出局不应成为跳过资源约束的通道。
修复要求
将“已知资源下限检查”与“完整月份资源合计”区分开：

1. 即使该月会因资金不足出局，已经计入工资的工作必须有对应工时与负担。
2. 已知用量超过任一额度，就足以判定 `plan_infeasible`。
3. 这种失败沿用年度试算原子性：没有可提交的结果账本或下一年状态。
4. 诊断写清月份、资源类型、额度、已知用量、超出量及主要活动，并说明这是已知下限。
5. 不能因通勤未知而跳过已经能确定的超限。
6. 也不能因已知下限未超限，就声称完整月份已通过资源检查。

出局月通勤：

* 明确没有到岗需求，例如全远程：通勤可以确定为零。
* 线下工作没有有效居住依据：保留未知，不补零，不擅自沿用上月住房或未支付成功的住房。
* 未知项与已知工作用量分别记录。
* 已知下限未超限、但完整用量无法确定时，可以继续保留资金 `exited` 结果，必须标明资源检查不完整。
* 没有获得的住房、食品和其他服务不得记为实际消费。
* 出局后的月份仍是“未发生”，不是完整的零负担生活月份。

用最少且清楚的字段区分“完整检查”“只检查已知下限”“未发生”。不要把一个布尔值同时解释成几种含义，也不要在摘要里将部分检查写成全部通过。
本轮不建立完整的出局居住模型，不重写工资和租金的收付时序。
五、F2：允许简单的多岗位工作
所有者裁决
一个分身可以打两份临时工。只要资金、时间和精力满足条件，就应允许执行。
不得仅因同月有两份线下工作而返回 `input_error`。
本轮通勤简化
沿用当前“住房到共同就业中心”的抽象，本轮采用：
每个实际执行岗位的每次到岗，分别计算一次完整往返；不同岗位之间不自动共享或合并行程。
因此：

```
工作小时 = 各实际岗位工时之和

通勤小时 =
    Σ（实际住房到共同就业中心的往返分钟
       × 该实际岗位的到岗次数 / 60）
```

说明：

* 当前每个岗位一天至多一次到岗，其到岗日数可作为该岗位的到岗次数。
* 跨岗位相加后得到的是“到岗次数/岗位到岗日累计”，不一定是不同的日历天数。
* 不把累计值错误命名为不同工作日，也不因累计值超过一个月的日历天数就直接拒绝。
* 每项岗位原有的日数、工作方式和工时一致性校验继续有效。
* 全远程岗位不产生工作通勤；混合岗位只按实际到岗部分计算。
* 同日连续上班可共享往返、不同工作地点间串行出行、每日班次冲突，仍未建模。

这是一项可审计的简化，不是关于现实路线的结论。它可能高估能共享通勤的多岗位者的出行成本，应写进“省略了什么、影响谁”。
实现要求

* 移除加载/计划检查与资源计算中的两处“一律拒绝两份到岗工作”规则。
* 工作小时、负担、工资分别汇总，税仍沿用既有合并计算规则。
* 按实际执行的岗位核算：缺货、资格不符等没有执行的岗位，不产生工资、工时或通勤。
* 住房兜底后，各实际岗位都按实际住房重新算通勤。
* 不允许保留工资，却让代理自行降低该岗位工时或到岗次数。
* 两份工作导致资源超限时返回 `plan_infeasible`，不是 `input_error`。
* 同一工作重复填写的结构校验继续保留；两份合法岗位与重复提交同一条行动应区分。
* 不建立日历、地图或路线规划器。

E1-3 的通勤满足感公式本轮不改。报告继续区分：
资源可执行，不代表现有通勤满足感评分已经支持。
六、家务残余：保留计算规则，补全含义
当前规则可以保留：

```
本人家务时间 =
    min（任务基准时间，各实际可用完整替代方案的残余时间）
```

明确：

* 残余是本人处理同一整项家务后仍需花费的整月时间；
* 不是机器运行时间，也不一定是每次操作时间；
* 洗衣机与代取服务如果都是完整洗衣任务的替代方案，不能把两份节省时间重复相减；
* “本人剩 3 小时”和“本人剩 1 小时”组合后取 1 小时，不得出现负时间；
* 服务没有买成，就不能获得相应替代效果；
* 免费服务或活动仍按明确的工时、负担记录核算。

该规则不负责表示洗衣机与烘干机等互补工序。未来需要时再拆子任务或定义组合方案，本轮不建立通用家务流程系统。
补充一条省略说明：当前基础家务量是声明的维持生活任务，尚不支持通过降低整洁程度主动减少家务。

八、验收与证据
必须覆盖的行为

1. 出局月时间超限：远程工作 80 小时、预算 60，返回 `plan_infeasible`，不留下工资账本或下一年状态。
2. 出局月精力超限：工作负担 80、额度 60，同样拒绝。
3. 资金对照：改变存款不能让已经确定的超负担劳动突然成为可执行劳动。
4. 部分检查：线下出局月通勤未知，已知劳动未超限时，保持资金出局但不声称完整资源可行。
5. 远程与后续月份：明确无到岗的通勤为零；出局后月份仍未发生。
6. 两份临时工成功：以独立审核反例为基础，两份 80 小时、各 10 次到岗的岗位，在明确的分别往返规则下可执行；正确合计工资、税、235 小时与 207 负担点。
7. 两份工作超限：分别构造时间超限、精力超限；必须是 `plan_infeasible`。
8. 混合与未执行岗位：远程不加通勤；混合只计到岗部分；未执行岗位不计资源。
9. 住房降级：多岗位全部使用降级后的住房分钟，不出现远处租金配近处通勤。
10. 精确边界：恰好等于预算通过；声明精度内的微小超额也拒绝，不添加容差。
11. 未安排时间：保留剩余记录，但不加分、不回血、不结转，也不强制把时间填满。
12. 家务与免费活动：完整替代取最小残余；未买成服务恢复家务；免费活动仍占时间。
13. 信息可见性：标准产品 payload 有足够的规划信息；显式隐藏权限继续生效；内部评分与真值继续隔离。
14. 确定性与原子性：同输入精确重放，失败不修改输入、不提交中途结果，成功跨年正确延续。
