**四、技术方案（已确认，按此实现）**

运行时依赖：`react`、`react-dom`、`react-router`、`@tanstack/react-query`、`ajv`（用 2020-12 版本的类）、`fraction.js`；Radix Primitives 只在复杂控件
确实需要时按单个组件引入（例如弹窗、下拉菜单），普通输入与按钮用原生 HTML。

开发依赖：`typescript`、`vite`、`@vitejs/plugin-react`、`vitest`、`jsdom`、`@testing-library/react`、`@testing-library/user-event`、
`@testing-library/jest-dom`、`@playwright/test`（只装 chromium）、`json-schema-to-typescript`；可选 `@axe-core/playwright`。

不用 React Hook Form（理由：表单库只记“字段值”，空输入是空字符串，它的“改过 / 碰过”不等于契约的四种答案状态，再加一层翻译最容易把“未答”和“0”

版本用开工当天的稳定版本，由 `package-lock.json` 锁定，报告里列出实际版本。Node 用本机已有的 22，包管理用 npm。文本文件用 LF 换行。

**五、模块：完成以下七组实现。**

**模块 A：契约层。**

1. `npm run contract:gen`：从 `contracts/product/v2/*.schema.json` 生成 TypeScript 类型到 `web/src/contract/generated/`，文件头写“由脚本生成，不要手改”。
   如果生成器不认 `$defs`，在生成脚本里做最小的预处理并在说明里写清，不手改生成结果。
2. `npm run contract:check`：重新计算每份 schema 的 SHA-256 与 `index.json` 对照，并确认重新生成的类型与仓库里的一致。不一致就失败，提示“共享结构变了：
   先重新生成类型，再检查用到这些字段的页面”。在 `build` 与 `test` 之前自动执行。
3. Ajv：导出的 schema 没有写 `$schema`，引用写成 `#/$defs/…`（pydantic 按 2020-12 规范生成），所以显式用 Ajv 的 2020 版本类，要能编译全部 13 份 schema。
   不开 `useDefaults`、`coerceTypes`、`removeAdditional`：校验只检查，不改数据（否则 `"30"` 会被转成数字、缺省值会被悄悄填进草稿）。样例 22 是
   `YearFacts` 片段，用 `ProductResult.schema.json` 里的 `#/$defs/YearFacts` 校验。
4. 测试：39 份样例全部按对应 schema 校验通过；适配器返回的每份消息、前端生成的每份草稿与提交消息都过校验。

**模块 B：业务访问层与样例适配器。**

1. 页面只依赖一个接口 `ProductApi`：`capabilities()`、`review(draft)`、`confirm(draft, acknowledged)`、`preflight(confirmedRef)`、`submit(submission)`、
   `progress(runId)`、`result(runId)`。确认请求在契约里还没有消息（需求文档 B1），本轮参数按“草稿 + 勾选的知悉项”写，注释指向需求文档。
2. `SampleAdapter` 按“场景”返回样例（对应表见下）。它只挑选并原样返回样例，**不做任何业务判断**：不匹配职业、不换算金额、不审阅、不判定合计、
   不算 C / E / M 或范围，也不改写样例。样例里没有的情况返回明确的“样例里没有这种情况”错误，不编造回复。
3. 提交：一个场景里第一次提交返回样例 07（accepted）；之后用**同一个**幂等键再提交返回 08（duplicate_same_run，同一个 run_id）；换了键就返回错误
   “样例只演示同一个幂等键的重复提交”（界面正确时不应出现，e2e 测试要断言它没出现）。样例回执里的 `idempotency_key` 是样例原值，E5-A 不拿它与
   界面生成的键比较，只用适配器的记录检查界面重复提交时用的是同一个键；E5-B 再核对服务端回执。“答案改过之后提交”场景返回 31。
4. 可以模拟传输层条件，用来测断线与重复提交：延迟、断网、“提交已送达但回执丢失”（适配器记下这次提交，再对界面抛网络错误）。这些只模拟网络，
   不改变业务结果。
5. 留一个 `HttpAdapter` 空壳和说明（E5-B 接 E3-C），不实现网络调用。

**模块 C：草稿与答案状态（这一轮的核心）。**

1. 草稿就是 `UserInputDraft` 的形状：一个 reducer 维护它，另存撤销记录，以“用户的一次操作”为一步（一次输入完成、一次挪分、一次均分、一次状态选择）。
   不另造一套表单值再翻译。
2. `meta` 照抄当前能力清单的 `meta`、去掉 `sample`；`draft_id` 在本标签页生成一次；`revision` 从 1 开始，每次内容变化加 1（这条规则等 E3 确认，需求 A8）。
3. 四种答案状态严格分开：
   - 定和分配：未答 = 没有这一项（或 `state: "unanswered"`，E3 两种都读成未答）；明确 0 = `provided` 且 `value_text: "0"`；无所谓 = `indifferent`；暂不确定 = `unsure`。界面用词照 E3 审阅：“还没有分配”
     “无所谓”“暂不确定”。不要在六维里用“无明显倾向”——那是健康题里一个可以确认的有效回答，用同一个词会让人以为六维也能这样提交。
   - 健康题：未答 = `choice` 为空；暂不确定 = `unsure`；无明显倾向 = `no_clear_tendency`（有效回答）。
4. 存储：只存当前标签页（sessionStorage），刷新后恢复；顶部有“清空我的答案”；页面写明“关闭这个标签页，答案就不保留”。存储内容带能力清单的版本与
   资料包指纹；版本不同时提示“问卷或资料版本变了，需要重新核对”，不静默迁移。
5. 确认之后再改答案：确认画像、预检查与运行按钮立刻标为“已失效（你在确认后改了答案）”，运行按钮变灰，需要重新确认。
6. 用户写的文字（现金、分数、职业、补充文字）一律原样保存，不自动格式化或“修正”。例：“3000,50”原样保留，提示金额写法规则（`money_input_rule_zh`），
   绝不变成 300050。

**模块 D：填写页面（四步）。**

第 1 步“范围与生活事实”：

- 顶部讲清这是怎样的模拟：能力清单的 `start_scenario`、`unsupported`、`limits` 原文。
- 城市：多选，只列 `selectable` 的城市；合成城加“样例”标识并显示 `note`。
- 职业：原文输入 + 职责候选卡（名称加职责，来自审阅的 `occupation.candidates`，不显示任何分类代码）。自由填写时写明“职业匹配要等 E3 服务，离线原型用
  样例演示”。
- 年龄：范围取能力清单的 `age_min`、`age_max`。
- 现金：金额原文 + 口径选择（只有 `money_bases` 里的选项，现在只有“2024 年美元，当地价格水平”）+ 含义说明（可动用的流动资金，不是总资产、信用额度或月薪）
  + `money_input_rule_zh` 提示。写明本版不能把今天的存款自动换算成 2024 年口径。
- 资格：契约还没有机器可读的“什么时候该问”（需求 A6），本轮放在默认折叠的“已经持有的资格（可选）”里，显示 `ask_when` 原文。

第 2 步“生活取舍”，分配器的行为：

1. 开始时每项都是“还没有分配”，没有数字；顶部写“还剩 100 分”，用 `aria-live="polite"` 播报变化。不预填、没有人格套餐；可选帮助里可以放例子，
   不自动填进去。维度顺序照能力清单，不重排。
2. 每一行：名称；“这是什么”（展开看 `definition` 与 `reference_improvement`，`support` 不是 `supported` 时显示 `support_note`）；文本输入
   （`inputmode="decimal"`，接受最多两位小数或规范分数如 `50/3`，规则文字取 `points.manual_entry`）；−/＋ 按钮（每次 5 分，旁边写“只是方便，不代表精度”）；
   “说不准”菜单（无所谓 / 暂不确定 / 清除）。
3. 计数：用 fraction.js 按用户原文精确相加（只算已提供、能解析的项），显示“还剩 x 分 / 已分完 / 多出 x 分”，x 按 `points.display_decimals` 显示，
   可以展开看精确值（例如 10/3）。不能解析的输入就地提示，不计入合计，也不改写。这只是填写辅助，正式合计以 E3 审阅为准。
4. 超过 100：不拦输入、不自动扣减。“多出 x 分”旁边给出“从哪一项减？”，列出当前有分数的其他项，用户点选后从那一项减去 x（那一项不够就减到 0，
   并提示还多出多少）。分满后再按某项的＋，同样先问“从哪一项挪 5 分？”。每次挪分是一次可撤销的操作。按钮或挪分算出来的新值：能写成最多两位小数
   就写小数（16.5 + 5 写 `"21.5"`），否则写约分后的规范分数（50/3 + 5 写 `"65/3"`）；不会小于 0。用户亲手输入的文字照原样保存。
5. 平均分配：要用户主动点；先弹确认（“每项精确 50/3，显示 16.7；这是你主动的选择，之后还可以改”），然后 `mode = "equal_split"`、`entries` 清空
   （E3 规定均分不能同时带手工数值）。之后改其中任一项时，先问“改成手动分配吗？其余各项保留精确的 50/3（显示 16.7）”；同意后 `mode = "manual"`，
   其余各项写 `"50/3"`，被改的那项写新值。物质内部同理（`100/3`）。这条交互规则等 E3 确认语义（需求 A8），报告里列为待确认。
6. 撤销：每组一个“撤销”按钮（“重做”可选）。
7. 物质内部：物质还没有分数或写法不对 → 折叠，提示“先给物质生活一个分数”；物质 = 0 → 折叠并标“不适用（物质为 0）”，已填的细分留在草稿里，物质改回
   正数时恢复显示；物质 > 0 → 展开，提示“这里分的是重要性，不是每月怎样花钱”。

第 3 步“健康与补充”：

- 健康三题：共同提示、题干与四个选项都取能力清单原文；不预选；“先跳过”就是未答；页面写明这三题不占 100 分，只供分身做计划参考。
- 补充文字：显示字数 n / 2000，超出变红、不截断；可以继续填写别的，确认页会把它显示成问题。
- 硬要求：只列 `hard_requirement_options`，范围与步长照抄，同一选项只能有一条；写明 `verification` 原文（单独核验，不拦截计划）。
- 品牌、菜系等属性偏好：按 `attribute_kinds` 提供可选条目，标“本版只记录，不评分”；可以勾“当作不可妥协”，勾上后显示“本版没有执行保障”的说明。
  条目挂在哪一项需求下（`need`），让用户从 `material_leaves` 里选——这与 E3 生成样例 17 的写法一致，但能力清单还没写明可选值（需求 A10）。
  `preference_id`、`requirement_id` 由界面按 schema 的格式生成（例如 `pref.1`、`hr.commute`）。

   健康每题的 `meaning`；`statements`；`issues` 做成问题卡（原因、影响、下一步、审计编号），带“去修改”。
