## 一、任务目标、范围与授权

## 三、F1：让状态绑定实际政策内容

### 已复现的问题

正常完成第一年后，分身取得第二年的 264.01 点额度。

保留 policy_id 和 version，只做以下修改：

- 把 mode 改为 disabled；
- 或把 alpha 从 0.10 改为 0.09。

当前代码仍允许第二年继续使用旧额度。

尤其是 disabled 情形：每月负担 255 的计划仍成功，到下一次交接才恢复成 250。观察接口还能将带着旧加成的状态标成：

- satisfaction_feedback = none；
- study_condition = static_text_understanding。

### 修复要求

1. 为政策建立稳定的内容身份，并让已产生的额度状态绑定它。可以采用规范化内容指纹。
2. 覆盖实际影响反馈行为的字段，至少包括：
   - 开关、alpha；
   - 公式、滞后、评分统计量、量化规则；
   - 评分规格身份与版本；
   - 产品陈述或研究真值的偏好来源；
   - 必要的协议或反馈版本身份。
3. 明确哪些说明性字段不参与内容身份，避免仅改说明文字就改变数学政策。规范化规则应确定、可重放，不依赖字典插入顺序或临时路径。
4. 加载、结算、观察复用一致性检查，避免三个入口各写一套判断。保持既有依赖方向。
5. 中途改变政策内容时明确拒绝，不静默恢复基础额度、不沿用旧加成，也不把它解释为分身生活不可行。
6. 从初始基础状态分别运行的合法实验臂必须继续可用。
7. 关闭反馈或 alpha=0 的运行，不能消费开启反馈产生的旧加成。
8. 不一致状态不得构造观察，更不能标为静态文字理解条件。隐藏精力数值也不能绕过。
9. 第一年、候选状态、正式下一年状态的绑定时点应明确，不能只保护结算而漏掉观察或交接。

目标是可靠识别当前协议下的误配，不需要建设通用政策管理系统。

## 四、F2：绑定同一次生活的账目、评分和候选状态

### 已复现的问题

同一人、同城、同年的两次真实试算：

- 近处住房：满足感约 0.560417，下一年额度 264.01；
- 远处住房：满足感约 0.539904，下一年额度 263.49。

当前存在两条误配路径：

1. 远处住房的 settlement + 近处住房的 score，可以生成反馈记录。
2. 近处住房的 feedback，可以应用到远处住房的候选状态。

两条路径都可能生成“远处住房的现金余额＋近处住房的精力加成”。

标准 `run_life_year` 当前当场结算并评分，没有发生这种混用；应保留这条正确路径。

### 修复要求

建立明确的一次年度交接关系：

年初状态及实际结算 → 对该结果的实际评分 → 反馈决定 → 对应的候选状态。

优先采用局部方案，例如在年度编排实际调用评分器时生成内部绑定对象，并在反馈生成和应用时核对。具体类型和函数名由你决定。

必须满足：

- 绑定在实际评分或年度交接产生时建立。
- 不能接收任意 score 和 settlement 后，仅给它们各算一次哈希，就声称已证明二者对应。
- 同人、同城、同年、同版本仍不足以认定同一次生活。
- 反馈只能应用到它对应的候选状态。
- 必要依据覆盖年初状态、实际结果及评分输入；说明具体核对了什么。
- 相同输入重放仍确定，不引入随机运行编号破坏重放。
- 重复交接不能叠加额度。
- 缺分、关闭、出局、终态等分支继续遵守原规则。

允许调整底层函数签名，将缺乏依据的旧调用方式明确拒绝。若收窄为唯一受支持的年度入口，必须同步修改调用点、测试和说明。

仅给函数名前加下划线或写“调用者应保证正确”，不足以关闭现有误配路径。也不要求实现抵抗任意人为伪造全部内部数据的安全系统。

新增内部对象及其序列化字典必须纳入现有信息隔离机制，不得直接进入代理观察。

## 五、产品支持边界与未来流程

### 1. 明确三种能力

分别说明：

- 生活能否执行：钱、时间、精力及其他执行条件是否满足；
- 满足感能否完整评分：正权重需求、城市资料与实际安排是否受支持；
- 下一年反馈能否确定：是否有原规则要求的完整年度分数。

支持边界针对“用户偏好＋城市资料＋行动组合”，不按用户身份简单划分。

例如：

- 两份工作分别可以执行，组合后的通勤评分却可能不受支持；
- 评分规则存在，但某座城缺少必要资料；
- 用户重视家务整洁，而现有评分尚未覆盖。

不得因为生活可以执行，就自动声称评分和反馈也完整。

### 2. 确立产品流程，正式接入留到 E1-7

在技术说明和 PLAN 登记以下流程：

1. 用户提供偏好、选择候选城市。
2. 运行前说明模型支持范围、已知缺口、合成参数及可能的停止情况。
3. 检查用户需求和城市资料是否满足本次比较要求。
4. 向分身提供当前产品模式可用的选择及组合规则。
5. 检查年度计划；超出支持范围的安排退回重做，具体重试机制由 E1-7 实现。
6. 执行后再次检查实际结果，保留生活事实、评分状态和反馈状态。
7. 单个分身不能继续时记录原因，其他不受影响的分身继续。
8. 结束后向用户报告完成情况、停止原因和结果适用范围。

本轮不实现前端，也不新增通用能力管理框架。优先复用现有目录、评分规格、覆盖报告和校验逻辑；记录正式接线位置。

### 3. 不得借限制范围改变用户或城市

- 不补未知分、不删除正权重需求、不重新归一化来制造完整评分。
- 用户本来给某项零权重时，遵守既有逻辑；不能由程序擅自改成零。
- 用户主动缩小本次比较范围，需要显式记录其选择及范围变化；本轮只登记流程，不实现交互。
- 不因一座城市评分较难，就悄悄改变它的评价标准。
- 统一的是行动定义、资料粒度和评价规则，不要求各城具有相同商品、价格或服务。
- 真实不可得、资料未知、模型暂不支持应分别说明。
- 不删除底层已有的多岗位执行能力。产品完整反馈模式的可用安排，可以比底层可执行范围窄。

### 4. 保持既有缺分规则

开启反馈且存在下一行动年，但缺少完整年度分数时：

- 保留当年已经完成的结算；
- 返回反馈信息不足；
- 不返回可直接执行的下一年状态；
- 不算生活出局或计划不可行。

关闭反馈或 alpha=0 时：

- 从同一初始状态单独运行；
- 不依赖完整评分即可继续结算；
- 未知评分继续未知，不因此获得完整总分或排名。

不得遇到缺分就自动关闭反馈，也不得让不同分身或城市因此悄悄使用不同政策。

运行前限制选择不能取代执行后的检查。未来疾病等事件可能让合法计划遭遇未覆盖情况，不能假定运行前校验可以保证所有轨迹完整。

## 六、单个分身停止与整场模拟的关系

### 1. 基本原则

单个分身的预期停止状态，不应自动结束所有其他分身。

例如未来 30 个都会区、每城 10 个分身的模拟中，一部分分身不能继续，其余分身仍可运行。整个批次最后可以是“执行结束、结果部分完整”。

这不等于宣布缺失不会影响比较质量。

### 2. 分清停止原因

复用既有状态，至少在报告中区分：

| 情况 | 含义 | 当前处理原则 |
|---|---|---|
| 正常到达终态 | 完成全部行动年 | 保存完整轨迹 |
| 生活出局 | 按模型规则付不起最低住房与食品 | 保留出局年月和已经发生的生活；这是模型内的生活结果 |
| 反馈信息不足 | 已结算，但无法完整评分或确定下一年额度 | 保留已完成结算，该分身停止推进 |
| 计划不可行 | 本次计划违反资金、时间或精力等执行约束 | 保留诊断；当前失败试算不生成生活账目；重试留 E1-7 |
| 输入、资料错误 | 当前输入或环境资料不满足要求 | 明确错误对象与影响范围，不记为生活失败 |
| 意外程序错误 | 实现或运行异常 | 保留错误信息，不能吞掉后当正常缺失 |

不能把它们统一写成“agent 没活下来”。

年度试算失败时，不得补造本年度生活；之前已经完成的年度记录也不能因此丢失。

### 3. 隔离范围

- 已明确属于单个分身的问题，只停止该分身。
- 已明确属于某座城市资料的问题，标记受影响的城市和分身，其余可继续。
- 若共享评分规格、统一单位或比较协议本身错误，应暂停受影响范围；不能把共同错误包装成多个独立分身的小问题。
- 不用一个捕获所有异常后直接跳过的循环来宣称完成隔离。
- 意外程序错误必须显式报告；不能未经判断就假定它只影响一个分身。

本轮不实现通用异常恢复或批处理平台。

### 4. 本轮的小型验证

利用现有年度入口和样例，在演示层运行一个小批次：

- 一个正常完成三年的分身；
- 一个评分缺失、反馈受阻的分身；
- 一个生活出局的分身。

验证：

- 后两个停止时，第一个仍能完成；
- 结果包含所有预定分身；
- 停止原因、最后完成的行动年及必要的月份信息清楚；
- 反馈受阻者保留当年结算；
- 生活出局者保留出局事实；
- 不给停止后的年份补分、补现金流或补行动；
- 三个分身分别单独运行与放在小批次运行，已有业务结果一致。

只需薄层演示循环与测试，不新增正式多分身 runner。运行异常的完整隔离策略在 PLAN 的 E1-7 中登记。

### 5. 运行完成与结论完整分开

报告至少保留：

- 每城原计划分身数；
- 正常完成数；
- 生活出局数；
- 反馈信息不足数；
- 计划未解决、输入或资料错误数；
- 意外程序错误数；
- 每个分身的最终状态与停止原因。

分类计数应互斥、能与原计划人数核对；更详细的原因可以另列。

不得：

- 把缺分统一记成零；
- 从记录中删掉未完成分身；
- 只计算完成者均值，就称为整座城市的平均结果；
- 自动补充新分身顶替停止者；
- 声称“每城停两三个不影响结论”。

本轮只报告状态和完整程度，不新增最终分数、阈值或城市排名。

在 E1-6 登记：

- 生活出局如何纳入三年期评价；
- 部分轨迹如何使用；
- 模型缺失与生活出局如何区别处理；
- 如何报告完成者统计与原计划总体的差别；
- 缺失是否集中在某类偏好或城市；
- 比较可靠性与敏感性分析如何展示。

这些规则应在使用结果作正式比较之前确定，不能看完排名再决定。

先对复制件运行，保留修复前结果。

- 不一致状态在加载、结算、观察处被识别；
- 旧加成不能误标为静态文字理解条件，包括隐藏额度时；
- 合法实验臂从相同初始状态正常运行；
- 同人同城同年的不同真实生活，交换评分、账目或候选状态被拒绝；
- 正确配对可交接，重复应用不叠加；
- 新增内部对象与原样字典不能进入代理；
- 缺分保留当年结算，开启反馈阻断、关闭反馈可继续；
- N=1、出局与终态不非法更新；
- 正常、反馈受阻、出局分身在小批次中互不错误终止；
- 所有预定分身都留在状态报告中，人数与分类可核对；
- 原有 A/B 正常演示和数值边界不退化。

先跑针对性测试，再跑全量离线回归与改动文件检查。金额、资源和既有确定性结果不加容差，不放宽旧评分测试。

做少量针对性变异检查，至少验证以下保护被破坏时，行为测试确实失败：

- 政策内容核对；
- 年度结果配对核对；
- 不一致观察状态的拒绝；
- 一个分身预期停止后，其余分身继续且停止者仍被记录。

变异只在临时副本进行。

证据保存到新的运行目录，拒绝覆盖。记录命令、环境、输入与源码指纹、反例、测试结果、兼容差异及提交依赖。

所有会写回结果的历史审核测试先复制。历史失败记录保持原样。

## 十、最终报告与审核点

按以下顺序用中文说明，让统计本科生可以审核：

1. 本轮修了什么、仍不能做什么。
2. F1 的生活例子：为什么“关了反馈却还用旧加成”被拒绝；合法关闭对照怎样运行。
3. F2 的生活例子：近房和远房的两次生活怎样防止串用账目、分数与状态。
4. “能执行—能评分—能更新精力”对照表，解释缺口在哪里。
5. 小批次例子：谁完成、谁出局、谁反馈受阻；为什么其他分身继续；哪些结果仍不能比较。
6. 正常演示哪些数字没变，哪些结构字段新增或变化。
7. 文件与依赖变化，以及实际测试、发现的问题和未解决事项。
8. 假设、省略、受影响的生活安排，以及 E1-5/6/7 的后续职责。
9. 证据路径、未来提交依赖和需要所有者审核的具体结论。

金额、小时、负担点和满足感分清单位。公式或指纹说明旁配一句生活含义。

不要用大段 JSON 或“全部通过”代替解释；不要把“其余分身继续跑完”说成“缺失不影响研究结论”。

完成后停在审核点，不进入 E1-5，不提交、不推送、不执行 `git add`。
