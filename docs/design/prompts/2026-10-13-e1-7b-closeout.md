三、F1：服务回复在首次调用、恢复和重放时采用一致校验
生活含义
一份计划第一次因为“来自错误模型”被拒绝，重新开机后仍然不能执行它。
归档不仅要证明“这里有一段回复”，还要证明“这是这个分身、这个年度、这份候选、这套设置对应的回复”。
已复现的问题

1. 服务返回合法计划，但 returned_model 与指定模型不同。
   * 首次运行正确停止；
   * 回复已被写成服务成功；
   * 恢复只看到成功记录，就接受并执行了这份回复。
2. 服务回复已保存、规划记录尚未写入时：
   * 改动归档中的请求正文、设置指纹或回复所属分身；
   * 恢复仍可能使用它。
3. 已执行年度的服务请求温度被修改，重放仍报告一致。
4. 缺少发送意图时虽然没有执行生活，但程序会写入暂停/程序错误记录，没有在写入前拒绝坏归档。

修复要求

1. 复用已有解析和指纹工具，建立共同的一致性检查，供新回复、缓存读取、恢复、重放使用。不要分别复制几套判断。
2. 核对至少包括：
   * 运行、请求、分身、年份、候选身份；
   * 服务尝试序号与合法的发送意图—结果配对；
   * 实际请求正文与模型设置；
   * 返回模型；
   * 原始回复、结束原因，以及重复记录或矛盾记录。
3. 必须覆盖“服务记录已经存在，但 calls.jsonl 尚未写入”的情形，不能只遍历已有规划记录。
4. 区分：
   * 服务成功返回并可能产生费用；
   * 这份回复是否允许用于规划。
错误模型返回的原文、模型身份、用量和费用都要保留，但首次运行、缓存命中、恢复均不能使用它。不能靠重试、换模型或丢掉费用记录掩盖。
5. 归档不一致时，在追加运行记录、执行生活或调用规划器之前拒绝；原文件保持不变。
6. 合法的已保存回复必须仍能零新增请求恢复，不能为了堵漏洞统一禁止恢复。
7. 检查针对工程错配与归档损坏，不建设防恶意伪造的复杂系统。

中断状态必须区分
根据实际持久化顺序，列一张小表说明如何处理：

* 已预留预算，但发送意图尚未落盘；
* 已写发送意图，尚无可靠回复；
* 费用已有核算，但回复尚未落盘；
* 合法回复已落盘，规划记录尚未写入；
* 规划记录已写入，但检查或年度执行尚未完成。

可能已发送但结果不明时，保留已有费用/预留并停止自动重发。不能把合法中断误称为损坏，也不能因恢复清零尝试次数。
四、F2：实际预算必须与声明及既有请求一致
生活含义
声明“本轮只能花这一本账里的钱”，执行器就不能拿另一本更宽松的账。
恢复运行时，昨天花过的钱不能因为流水缺失而被当成没花过。
已复现的问题

* 配置声明最多一次请求，实际规划器注入另一份上限更高的预算，正式入口仍发出两次请求。
* 已完成一次调用后，临时账本流水被清空；恢复继续发送请求，归档有两次请求，预算只记一次。

正常 CLI 当前组装正确，但正式入口缺少一致性保护。
修复要求

1. 发送前核对规划器实际持有的预算与运行声明：
   * 请求上限；
   * 金额上限；
   * 报价内容与版本；
   * 实际解析后的账本位置及必要身份。
不能仅比较名称、price_version 或调用方另外传来的声明对象。
2. 恢复前，按完整的运行/请求/服务尝试身份，核对当前运行的服务记录与预算历史。
3. 发现错账本、缺预留、缺少应有核算或费用矛盾时，在新增请求前停止；不能将其解释为空白预算，不能猜测补回费用。
4. 共享账本可以合法包含先导、主试跑和其他授权运行：
   * 核对当前运行应有的条目；
   * 总额度仍按整本账计算；
   * 不要求整本账只包含当前运行，不删除其他运行记录。
5. 合法中断中的未决预留继续占用额度；一次调用不能重复核算、重复预留或重复扣除。
6. 仍只支持串行，不在本轮实现数据库或并发账本。
7. 只读重放不能为了检查而创建或修改真实账本，也不要求 API key。生活重放与付费对账分别报告，不能混称。
8. 新测试全部使用临时配置和临时账本，原真实预算一字节不改。

五、F3：公开税说明与实际税表一致
已复现的问题
合法税表第一档税率为 10%，收入 1500 时环境正确算税 150，但给模型的文字仍说“第一档不扣税”。
修复要求

* 根据实际税表生成正确说明，或使用不假定第一档免税的通用表述。
* 继续从环境实际使用的同一份税政策投影，不另写一套税表或计税算法。
* 至少验证第一档 0% 与第一档 10% 两种情况；核对累进税文字不会被理解为对全部收入套最高税率。
* 当前真实试跑第一档确实为零，不能把这次发现描述为历史试跑已经算错税。
* 公开说明属于模型输入。若发生变化，明确记录提示身份、请求指纹和版本的变化，不偷偷改写历史请求。
