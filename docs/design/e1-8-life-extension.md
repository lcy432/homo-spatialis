# 生活扩展：完整食品方案、个人消费与享受、装备与爱好（E1 + E3）

裁决见 [ADR0041](../../DECISIONS/0041-life-extension-food-enjoyment-hobbies.md)（第三节是独立审核 R1–R9 的收尾修复）；参数见[参数与假设目录](parameter-assumption-register.md) SC-21–SC-25、PI-26–PI-27、EV-19、AG-04、AG-17、AG-23。所有数值都是合成探索设定，不能据此排序真实城市。

## 1. 做什么

分身在合成世界里多了三种生活：

* **吃饭是一个月的完整方案**：例如“每周 17 顿自己做（10 顿新鲜）+ 4 顿意式外食”。月费、做饭与外食时间、饮食评分都读同一份方案。
* **个人消费与享受**：舒适椅、坐垫这类居家舒适用品（在用就有），按摩这类享受型服务（按实际次数）。
* **装备与爱好**：吉他提供“能弹吉他”的能力，练琴是一次活动；网球套餐自带球拍，只对这一次有效；自己买的网球拍能用 5 年。

不变的老规则：偏好不是开支比例；贵不等于更好；买不起不等于不喜欢；花钱、成交与持有本身不加分；“没发生”“资料未知”“模型不支持”分开报。

## 2. 数据形状（`src/common/life_contracts.py`）

| 事实 | 字段 | 检查 |
|---|---|---|
| `FoodPlanFacts` | 是否覆盖一个月基本饮食、每周餐数、各部分（自己做 / 外食 / 外送、餐数、新鲜餐数、菜系）、做饭小时、外食小时 | 可得的方案必须是完整方案；做饭 + 外食小时 = 资源账小时；每个组成**必须写**新鲜餐数与菜系：0 是确定没有，`null` 是资料未知，不写就拒绝 |
| `EnjoymentProvision` | 功能、方式（`passive_service_month` 在用即有 / `service_units` 每月份数） | 耐用品只能是在用即有；功能要在词表里 |
| `EquipmentFacts` | 提供的能力 | 只能挂在耐用品上；能力要在词表里 |
| `ActivityFacts` | 主类别、标签、参与小时、准备往返小时、需要的能力、套餐本次提供的能力、是否替代正餐 | 参与 + 准备往返 = 每次资源小时；是否替代正餐**必须写**（0），大于 0 拒绝 |
| `ActionItem.months` | 一项体验在不连续的几个月参加 | 严格递增；不另造编号、不去掉唯一性检查 |
| `ParticipationRecord` | 每项活动每个请求月一条：完成 / 暂停 / 没能进行、次数、参与与往返小时、用到的装备、套餐能力、原因 | **唯一的参与事实**：时间账、休闲评分、反馈与记忆都读它 |

## 3. 钱、一次参与和一件装备怎样流动

**结算顺序**（`src/econ/life_settlement.py`）：每月先付住房与食品（最低生活检查只检查、不另扣），再按计划顺序执行其他行动；**需要持有能力的活动**推到当月一次性购买之后。所以“吉他排在练琴后面”与“吉他排在前面”结果相同。

一把吉他（K51，240，寿命 3 年 = 36 个月）的一生：

1. 第 2 月买下：扣 240，生成持有物，当月生效；
2. 第 2 月练琴 2 次：`_capabilities_now` 查有效持有物（不扣寿命），找到“能弹吉他”，记一条参与：完成、2 次、4 参与小时、用到 `k51.durable.guitar`；
3. 月末资源账从这条参与记录取次数与小时（参与 4 + 往返 0 小时，每小时负担照旧取资源事实）——不再从计划另算一遍；
4. 寿命只按服务月扣：第 2–12 月共 11 个月，年末剩 25 个月，跨年不重置；
5. 买失败、病中按应急安排取消、下一年才生效、已到期：都没有能力，这个月的练琴记“没能进行”，不收费、没有小时、不计分；生病暂停的月份记“暂停”，同样没有费用、小时与收益；
6. 到期之后可以在晚于到期的月份再买一把（两段服务月不重叠）；还在服务期内再买同一件仍然拒绝。

一次性享受服务（例如单次按摩）只有享受事实、没有活动事实：生病暂停时只记暂停、不付款、那个月没有享受；不写参与记录。

## 4. 评分（`src/econ/life_scoring.py`，评分版本 `e1-life-v1`）

物质 M = Σ 物质权重 × 四项分数（居住空间、饮食生活、日常生活便利、个人消费与享受）；B 与 S = (1 − γ)B + γH 不变。每项 s = min(c, z/(z + τ))。

| 分项 | z | 手算 |
|---|---|---|
| 饮食生活 | 1 × 每周新鲜餐 + 0.5 × 每周合口味餐（τ 7） | 基本方案 3 顿新鲜 → 0.3；川味家常（21 顿全川菜、10 顿新鲜）对确认川菜的人 → 20.5/27.5；新鲜餐明确写 0 → 10.5/17.5；新鲜餐数 `null` → 未知（不是 0.6） |
| 个人消费与享受 | Σ η_f v_f：居家舒适在用 1.5，放松护理每次 1.0（τ 3） | 舒适椅 1.5，椅 + 坐垫仍 1.5，椅 + 每月 2 次按摩 3.5 → 3.5/6.5 |
| 休闲 | 城市背景 4 + 参与小时 ×（1 + 0.5 × 主类别匹配）（τ 12） | 合唱 2 小时：确认音乐的人 7/19，中性 6/18；没有活动的月份两人相同 |

价格、档次、外食次数不是输入；外食只在饮食项计分，烹饪课只在休闲项计分；纯装备没有享受功能；同一参与拆成几条记录得分与时间都不变；次要标签不再乘。菜系未知只在用户确认了菜系时让饮食评分未知。

**覆盖报告**（`src/econ/life_coverage.py`）与评分器共用同一份事实判断（`food_plan_gaps`、`experience_gap`、`unsupported_enjoyment`）：可选的食品方案缺事实、实际参加时无法评价的体验是资料缺口；词表外的享受功能是“模型未支持”，单独列出；没有购买、没有参加是确定的 0。覆盖说的是可选目录，某条实际生活没有用到缺口方案时照样可评分。

## 5. 期末参考生活（`src/econ/life_terminal_value.py`，评价版本 `e1-life-evaluation-v3`）

每个模板每月安排 4 次音乐练习，按**能力**使用期末持有物（任何在服务期内、能弹吉他的都算，商店现在卖不卖不影响）：

* 持有物覆盖整个 12 个月 → 照用；
* 只剩 r 个月 → 前 r 个月照用，之后基本模板停止、较舒适模板在第 r + 1 个月换一把；
* 没有这项能力 → 不买、不安排。

较舒适模板另有每月一次按摩；期末在用的舒适用品照常提供功能。两座城同一套槽位与模板；L/V/J 公式不变，购买价不进估值。

**估值范围说明**（`equipment_valuation_scope`）：期末持有的每件装备，模板考虑了哪些用途、哪些没有。公开结果里每个分身有 `valuation_scope`：吉他写“参考生活按它的能力继续安排相应活动”，网球拍写“参考模板没有考虑它的用途……不是说这件装备没有价值”。这只是范围说明，不改 V，也不让分身因此归 M。

## 6. 信息隔离与请求长度（`src/agentlayer/life_views.py`）

## 7. 接入层（E3）

* 物质四项（词表 `e3a-vocabulary-v2`）；公共结构 `e3a-product-schema-v3`，旧确认重新审阅。
* 兴趣与口味（`src/product/interests.py`）：文字按资料包别名切片成候选，有歧义的列出、没认出的原样保留；**选中**才进入画像；只有文字没有选中时审阅阻断；同一类别选两次在审阅阶段就拒绝。不管选了哪种作答状态，原文都保留（只写“喜欢冲浪”再改选通用评价，原文留存为本版未支持的描述）。作答状态分开：未答 / 暂不确定 / 没有固定爱好（没有偏好）/ 通用评价 / 确认。没有按具体兴趣或口味个性化时，用户要知悉 `ack:interests_not_personalized`（复用审阅的待确认机制，不强迫填写爱好）；预检查的 `scope_zh` 与结果的 `limitations_zh` 逐项写明这次按什么个性化、哪些没有。品牌只留存。
* 生活扩展候选的编译检查（`src/product/life_items.py`，`e3-life-item-compiler-v2`）：“局部结构合法”不等于“能交给 E1 执行”。依次查限制（调用方转来的与候选自己携带的资格、年龄、日期字段）、契约、种类与事实、可得性、词表，再把候选放进这座城目录的副本跑 E1 的目录、跨对象与可结算检查并核对执行角色——可执行 / 拒绝 / 不可得 / 本版未支持 / 资料未知；不补任何数值；编译结果有自己的内容身份。**现在只有受控样例**，还没有接 intake-02 的真实资料导出。

## 9. 省略了什么、影响谁

* 真实资料（intake-02）没有做饭时间、每周新鲜餐数、活动参与时间与无日期的活动，相应机会不能编进 E1；本轮只在合成样例上可执行，编译检查也还没接真实导出。
* 菜系与兴趣只有很小的合成词表；说法不在别名里的人得到“没认出”。
* 匹配系数是统一的模型假设，不是对个人的测量；真实模型会不会据此安排生活没有验证。
* 期末模板只覆盖“音乐练习”这一种装备活动；网球拍等其他能力在结果里写成范围说明。
* Haiku 5.5 的上下文长度本机没有核对记录，按 200,000 的保守下界定上限；最坏情况的修订请求只剩约 2,200 token 的余量。
