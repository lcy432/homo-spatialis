## 二、算出了什么、没算出什么

**已落盘**

- 五个网格点的 M1（总体均值）、M2（总体协方差）、M3（个体后验，max 口径）及 8 次随机化之间的标准差（JSON 字段名 `se`，实际是组间样本标准差，**不是置信区间**）。
- 每个网格点的有效样本量：中位数稳定在 R 的 2.9%（R=200 时 3.7%）。
- R=200 的逐人 M3 分布：中位 3.36e−2，1000/1000 超容差。

**未落盘**

- **高 R 端的逐人分布。** 运行时代码把分布点写死为 `(200, 3200)`，本次网格没有 3200，所以 `m3_distribution` 只有 `"200"`。JSON 里 `m3_is_a_max` 那句"分位数见 m3_distribution"对高 R 不成立。
- 因此"换中位数口径够不够"**只有按 1/√R 的外推，没有实测**。

**未验证**

- **`R_fit = 200` 的充分性。** 本检查固定拟合参数，只能支持后验与总体矩的积分精度。JSON：`R_fit_at_200: not_tested_by_this_check`。
- 参照点 R\* 只用了一次随机化，它自身也有误差；表中数值未独立复现。

## 三、日志标题与 JSON 的冲突

`logs/rpost-study.log` 第 9 行写 `参照点 R* = 12800`，JSON 写 `"R_reference": 60000`。**实际用的是 60000，日志标题错了。** 原始日志保持原样，不改写。

依据，按强弱排列：

1. **代码**：运行时版本里，标题打印读默认常量 `R_REFERENCE = 12_800`（第 144 行），参照求值读 CLI 参数 `args.reference`（第 147 行），JSON 字段也读 `args.reference`（第 256 行）。标题与计算读的是两个不同的变量。`f536761` 只改了第 144 行这一处，把标题改为读 `args.reference`。
2. **计时，独立于代码的旁证**：五个网格点的单次随机化耗时对 R 线性，过原点拟合 8.83 ms/点。按此预测 R\*=60000 需 530 s、R\*=12800 需 113 s；日志记录的参照段实测 **531 s**，计时起点就在参照求值之前（第 145 行）。
3. **对照**：`--reference` 参数出现之前那次运行（`integration-precision.json`）的 `R_reference` 是 12800，那一次的标题是对的。
4. **命令**：会话记录里的启动命令带 `--reference 60000`。

**确认不了的部分**：仓库里没有保存这次运行的 argv。"运行进程加载的就是 `bc0e49b` 里那个版本"依赖会话里的操作顺序：启动之后到 `bc0e49b` 提交之间没有改过这个文件。第 2 条计时证据不依赖这个前提。

**日志在 git 里显示为"已修改"的原因**：`f536761` 提交时这次运行还没结束，把日志的中途快照（到 R=3000 那行为止）一起收了进去。当前文件在内容上是那份快照的**纯追加**，唯一的字节差异是换行符（进程写 CRLF，git 提交时转成 LF）。

## 四、本轮对代码的唯一改动

把分布点从写死的 `(200, 3200)` 改为 CLI 网格的首尾：`dict.fromkeys((args.grid[0], args.grid[-1]))`。

检查：diff 只含这一处加注释；`py_compile`、`ruff check`、`ruff format --check` 通过；`--help` 能解析；选点表达式在四种网格下的行为如预期（单点网格去重为一个点）。没有测试引用这个脚本。**没有补跑**。

**它有一个副作用**：在**默认**网格 `[50, …, 3200]` 下，低端分布点从 200 变成 50。而 R=200 正是历史判定 `R_post @200` 所在的点。今后若要复现 R=200 的分布，显式传 `--grid`。
